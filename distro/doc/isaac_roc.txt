----------------------------------------------

1) Что мы делаем? (Переход на аппаратный ISP)
Мы меняем парадигму обработки. На плате Orin Nano есть ISP (Image Signal Processor) 
— это отдельный аппаратный блок, независимый от CPU и GPU.


Прямо сейчас твой конвейер выглядит так:
Матрица -> CSI-интерфейс -> RAM -> CPU (Python + OpenCV дебайеринг) -> ROS2 топик.

Это грузит процессор, а на выходе 
ты получаешь просто ч/б кадр без цветокоррекции, 
баланса белого и шумоподавления (что для картинки пилота — боль).


Переход на ISP означает следующий конвейер:
Матрица -> CSI-интерфейс -> аппаратный ISP (Дебайеринг, AE, AWB, шумоподавление) -> Shared Memory (Zero-copy) -> ROS2 топик.

Результат: 
    * Идеальная, насыщенная цветная картинка для пилота с
    аппаратным авто-экспонированием.

Нагрузка на CPU падает практически до нуля.

Кадры передаются в память GPU без лишнего копирования (Zero-copy).

---
Важный нюанс для VINS-Mono:
---
ISP обычно выдает картинку в формате NV12 (или YUV). 
    Прелесть NV12 в том, что его первая часть (Y-канал) — это идеальная, 
    уже отфильтрованная монохромная картинка. 
    То есть тебе не нужно будет тратить ресурсы на конвертацию цвета в ч/б для VINS, 
    достаточно просто забрать Y-канал.



Главное решение: isaac_ros_argus_camera
Это официальный пакет NVIDIA для ROS2, который делает ровно то, что тебе нужно.
Он использует библиотеку libargus (низкоуровневое API для доступа к аппаратному ISP Jetson) и технологию NITROS (аппаратно-ускоренные сообщения).

Что он дает: 
    Читает данные с камеры напрямую через ISP, 
    аппаратно их обрабатывает и публикует стандартные 
    sensor_msgs/Image и 
    CameraInfo 
        (параметры калибровки можно подсунуть ему в конфиг).

Производительность: Работает на скоростях, недоступных для OpenCV в Python, 
не трогая ядра CPU.


Альтернатива (без Isaac ROS, но с ISP): gscam + GStreamer
Если по какой-то причине тянуть контейнеры Isaac ROS не хочется, 
    в ROS2 есть пакет gscam или ros2_shared_camera. 
    В них можно прописать GStreamer-пайплайн с использованием плагина 
    nvarguscamerasrc.
Пайплайн nvarguscamerasrc ! nvvidconv ! ... 
делает то же самое — пропускает кадр через аппаратный ISP.


Главный подводный камень (Hardware / Drivers)
Чтобы использовать ISP (через Argus или GStreamer), 
камера обязательно должна поддерживаться на уровне Device Tree (DTB) 
и иметь ISP-тюнинг файл (калибровку цветов/линзы от производителя).

Твой текущий скрипт использует v4l2 напрямую. 
Иногда производители (включая Arducam) предоставляют драйверы, 
которые работают только в сыром v4l2-режиме, 
в обход встроенного ISP Jetson. 
Если драйвер стоит неправильный, Argus просто не увидит камеру.

Камера AR0234 аппаратно поддерживается NVIDIA, 
    но требует правильной установки драйвера от Arducam с поддержкой libargus.

Камера сейчас определяется у тебя при вызове команды nvgstcapture-1.0 
    (это стандартная утилита NVIDIA для проверки ISP), 
    или она видна только через v4l2-ctl?

----------------------------------
Вариант 1.
Пайплайн GStreamer через gscam2 (Самый гибкий и производительный метод)
----------------------------------

    Этот подход идеален, если цветной поток для пилота 
    нужно не просто пустить в ROS2, 
        а сразу закодировать (H.264/H.265) для отправки по радиоканалу 
        через систему цифровой связи, минимизируя задержку.

    С помощью элемента tee в GStreamer 
        поток раздваивается прямо в памяти GPU (NVMM), 
        исключая лишнее копирование кадров.

Пример концептуального пайплайна для ROS2-ноды gscam2:

nvarguscamerasrc sensor-id=0 ! \
video/x-raw(memory:NVMM), width=1280, height=720, format=NV12, framerate=30/1 ! \
nvvidconv ! \
tee name=t \
  t. ! queue ! video/x-raw(memory:NVMM) ! nvvidconv ! video/x-raw, format=BGRx ! videoconvert ! format=MONO8 ! appsink name=sink_vins \
  t. ! queue ! video/x-raw(memory:NVMM) ! nvv4l2h265enc bitrate=4000000 ! h265parse ! rtph265pay ! appsink name=sink_pilot



Как это работает:

nvarguscamerasrc: Запускает камеру, включает аппаратный ISP, выравнивает экспозицию на лету и выдает цветной NV12 в память NVMM.

tee name=t: Моментально клонирует указатель на область памяти GPU.

Ветка VINS (sink_vins): 
    Берет кадр, с помощью аппаратного конвертера nvvidconv 
    отсекает цветовую информацию (или берет только Y-канал) 
    и передает в ROS2 чистый монохромный mono8 с минимальной задержкой.

Ветка пилота (sink_pilot): 
    Тот же кадр параллельно уходит на аппаратный кодировщик nvv4l2h265enc. 
    Процессор вообще не участвует в сжатии видео. 
    Этот поток можно транслировать напрямую в интерфейс связи 
    (например, через OpenHD / RTP) минуя тяжелую сериализацию ROS2.



----------------------------------
Вариант 2.
Экосистема Isaac ROS (Полностью внутри ROS2)
----------------------------------

Если оба потока критически необходимы именно внутри графа ROS2 
(например, цветная картинка пишется в rosbag2 
или обрабатывается нейросетью на Jetson перед отправкой), 
используется стек Isaac ROS.


Для этого связываются две ноды в рамках одного контейнера/процесса в виде 
Composable Nodes (чтобы передавать сообщения через Shared Memory без копирования).

---
isaac_ros_argus_camera (Пакет isaac_ros_argus_camera)
---
    Заменяет твой текущий Python-скрипт.
    Напрямую общается с ISP.
    Публикует цветной поток 
        (обычно в формате bgr8 или rgb8, аппаратно сконвертированный из NV12) 
        в топик /image_raw.
    Синхронно публикует правильный /camera_info 
        (параметры калибровки считываются из настроек ноды).


---
isaac_ros_image_proc (Пакет isaac_ros_image_proc)
---
    Эта нода подписывается на /image_raw.
    Используя тензорные ядра или GPU, она выполняет операцию ColorConvert.
    На выходе генерируется топик /image_mono для VINS-Mono.

Пример структуры launch.py файла для Isaac ROS:


import launch
from launch_ros.actions import ComposableNodeContainer
from launch_ros.descriptions import ComposableNode

def generate_launch_description():
    # Нода захвата Argus (работает с ISP)
    argus_camera_node = ComposableNode(
        package='isaac_ros_argus_camera',
        plugin='nvidia::isaac_ros::argus_camera::ArgusCameraNode',
        name='argus_camera',
        parameters=[{
            'camera_id': 0,
            'output_format': 'bgr8',
            'camera_configuration': '1280x720_30fps'
        }],
        remappings=[('image_raw', '/camera/pilot/image_raw')]
    )

    # Нода аппаратной конвертации в монохром для VINS
    vins_mono_node = ComposableNode(
        package='isaac_ros_image_proc',
        plugin='nvidia::isaac_ros::image_proc::ColorConvertNode',
        name='color_convert_vins',
        parameters=[{
            'output_encoding': 'mono8'
        }],
        remappings=[
            ('image_raw', '/camera/pilot/image_raw'),
            ('image_mono', '/camera/vins/image_mono')
        ]
    )

    container = ComposableNodeContainer(
        name='camera_container',
        namespace='',
        package='rclcpp_components',
        executable='component_container_mt', # Многопоточный контейнер
        composable_node_descriptions=[argus_camera_node, vins_mono_node],
        output='screen'
    )

    return launch.LaunchDescription([container])

    Если ты работаешь внутри официального Docker-контейнера Isaac ROS,

камера обязательно должна поддерживаться на уровне Device Tree (DTB) 
и иметь ISP-тюнинг файл (калибровку цветов/линзы от производителя).

DTB нужет только для
Вариант 1.
Пайплайн GStreamer через gscam2 (Самый гибкий и производительный метод)

или DTB нужен и для
Вариант 2.
Экосистема Isaac ROS (Полностью внутри ROS2)

Тоесть DTB нужен в обеих случаях?

----------------------------------------------------------------------


Да, DTB (Device Tree Blob) и файл ISP-тюнинга строго необходимы в обоих случаях.

И gscam2 (через GStreamer nvarguscamerasrc), 
и isaac_ros_argus_camera — это просто высокоуровневые интерфейсы для ROS2.
Под капотом они оба стучатся к одному и тому же закрытому системному демону 
NVIDIA — nvargus-daemon (используя API libargus).

Вся архитектура захвата на Orin Nano выглядит как слоеный пирог:

    Уровень железа (DTB): 
        Сообщает ядру Linux, на каких физических линиях MIPI CSI висит матрица, 
        какой у неё I2C-адрес для управления регистрами, 
        сколько линий данных используется и какие нужны частоты. 
        Без правильного DTB ядро не поднимет сенсор.

    Драйвер ядра (v4l2): 
        Обеспечивает низкоуровневую передачу сырых данных в память.

    Уровень ISP (nvargus-daemon + файл тюнинга): 
        Демон перехватывает сырой поток. 
        Чтобы правильно превратить сырой Байер в цветную картинку 
        (сделать дебайеринг, убрать виньетирование линзы, настроить баланс белого), 
        ему критически нужен файл тюнинга 
        (обычно лежит в /var/nvidia/nvcam/settings/).

    Уровень приложения (GStreamer / Isaac ROS): 
        Просто говорят демону: 
            «Инициализируй сессию и отдавай мне готовые кадры в память NVMM».

Если в Device Tree нет правильного описания камеры или отсутствует файл ISP-тюнинга,
nvargus-daemon не сможет инициализировать сенсор. В результате и GStreamer пайплайн,
и нода Isaac ROS упадут с ошибкой при попытке создать сессию захвата.



Что это значит на практике для AR0234?
Arducam обычно предоставляет свои драйверы в виде .deb пакетов 
или скриптов установки (вроде install_cam.sh). 
Этот софт делает именно то, что нужно: он патчит DTB под конкретную версию JetPack 
и подкидывает файлы тюнинга в системные папки.

Как проверить, что DTB и ISP-тюнинг уже настроены правильно?
Прежде чем поднимать ROS2, закрой свой текущий скрипт, 
чтобы освободить /dev/video0, и выполни в консоли стандартную утилиту NVIDIA:

nvgstcapture-1.0



(Если работаешь без графического интерфейса, можно перенаправить вывод в файл: 
    nvgstcapture-1.0 --automate --capture-auto)

Если захват пошел и ты видишь красивую, цветную картинку 
    с работающей автоэкспозицией — всё отлично.
    DTB прошит, ISP работает, можно смело поднимать GStreamer или Isaac ROS.

Если команда падает с ошибкой или виснет — это означает, 
    что драйвер от Arducam работает только в raw-режиме (v4l2), 
    а для libargus камера невидима. 
    В этом случае придется переустанавливать/обновлять драйвер Arducam 
    до версии с поддержкой ISP Jetson.

Но ошибка -bash: nvgstcapture-1.0: command not found — это очень важный красный флаг, 
который нам нужно решить до запуска Docker.

Почему это критично?
Docker не умеет сам «общаться» с железом камеры. 
Контейнер Isaac ROS работает так: 
    он ищет специальный сокет (/tmp/argus_socket), 
    через который связывается с системным демоном nvargus-daemon,
    работающим на хостовой ОС.


Если на хосте нет утилиты nvgstcapture-1.0, это означает одно из двух:

Либо у тебя установлена базовая Ubuntu без пакетов NVIDIA L4T (JetPack BSP), 
    отвечают за мультимедиа и работу с аппаратным ISP.

Либо драйверы Arducam для AR0234 не установлены на уровне ядра (DTB не пропатчен).

но на хосте ещё не сгенерирован файл-паспорт (CDI-спецификация),

Ошибка unresolvable CDI devices nvidia.com/pva=all 
возникает из-за аппаратных отличий.

Jetson Orin Nano — это единственная плата в линейке Orin,
у которой физически вырезан блок PVA (Programmable Vision Accelerator) и блок DLA.

Однако разработчики NVIDIA в скриптах isaac_ros_common 
по умолчанию прописали жесткое требование монтировать PVA для всех плат.

Docker пытается пробросить несуществующий чип внутрь контейнера и ожидаемо падает.
Нам нужно просто вырезать эти флаги из скриптов запуска.


cd ~/workspaces/isaac_ros-dev/src/isaac_ros_common

# Вырезаем требования PVA
find . -type f -exec sed -i 's/"--device=nvidia.com\/pva=all"//g' {} +
find . -type f -exec sed -i 's/--device=nvidia.com\/pva=all//g' {} +

# Заодно вырезаем DLA (у Orin Nano его тоже нет, чистим заранее, чтобы не было следующей ошибки)
find . -type f -exec sed -i 's/"--device=nvidia.com\/dla=all"//g' {} +
find . -type f -exec sed -i 's/--device=nvidia.com\/dla=all//g' {} +


# Подменяем PVA на GPU во всех файлах
grep -rl "nvidia.com/pva=all" ~/workspaces/isaac_ros-dev/src/isaac_ros_common | xargs sed -i 's/nvidia.com\/pva=all/nvidia.com\/gpu=all/g'

# Подменяем DLA на GPU (его на Orin Nano тоже нет)
grep -rl "nvidia.com/dla=all" ~/workspaces/isaac_ros-dev/src/isaac_ros_common | xargs sed -i 's/nvidia.com\/dla=all/nvidia.com\/gpu=all/g'

А так, что бы собрать образ где только бинарники - не?


Да, это не просто можно, это отраслевой стандарт для продакшена 
    (называется Production-образ или Многоэтапная сборка / Multi-stage build). 
    Тащить на боевой дрон исходный код, тяжелые компиляторы (вроде nvcc), 
    заголовочные файлы (.hpp) и гигабайты кэша сборки (build/) — плохая практика.

В ROS2 вся прелесть в том, что после успешного выполнения colcon build всё,
    что нужно для работы нод, собирается в одну-единственную папку — install/. 
    Папки src/, build/ и log/ для работы дрона больше не нужны.

Вот два способа сделать чистый образ, где будут только бинарники 
    (скомпилированные .so файлы и исполняемые файлы).


---------------------------------------------------------------

и упаковать то, что осталось.

---

rm -rf src/ build/ log/

Теперь в воркспейсе осталась только папка install/ со скомпилированными бинарниками.

---

---
Сохраняем контейнер в чистый образ:
---

На хосте смотрим ID контейнера (через docker ps -a) и делаем коммит:

    уже не будет содержать твоих исходников, 
    а папка install/ будет намертво зашита внутрь. 
    На остальных 99 дронах тебе достаточно будет просто запустить этот образ 
    и сразу вызвать ros2 launch.




--------------------------------------------------------------- 
Вариант 2. Профессиональный (Multi-stage Dockerfile)
---------------------------------------------------------------  

Если планируется обновлять софт, автоматизировать сборку (например, через CI/CD) 
и полностью исключить человеческий фактор, пишется специальный Dockerfile, 
который состоит из двух этапов: этапа сборки (Builder) и этапа запуска (Runner).

Создается файл Dockerfile.prod в корне проекта:


# === ЭТАП 1: СБОРКА (Тяжелый образ со всеми инструментами) ===
FROM nvcr.io/nvidia/isaac/ros:aarch64-ros2_humble_4c0c55dddd2bbcc3e8d5f9753bee634c AS builder

# Настраиваем окружение для CUDA
ENV PATH=/usr/local/cuda/bin:$PATH
ENV LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH

WORKDIR /workspace
COPY ./src ./src

# Компилируем софт
RUN colcon build --symlink-install \
    --cmake-args -DCUDA_TOOLKIT_ROOT_DIR=/usr/local/cuda -DBUILD_TESTING=OFF

# === ЭТАП 2: ПРОДАКШН (Чистый образ без исходников) ===
FROM nvcr.io/nvidia/isaac/ros:aarch64-ros2_humble_4c0c55dddd2bbcc3e8d5f9753bee634c

WORKDIR /workspace

# Копируем ИЗ ЭТАПА СБОРКИ только готовую папку install
COPY --from=builder /workspace/install ./install

# Настраиваем автозапуск (DDS и source) в bashrc контейнера
RUN echo "source /workspace/install/setup.bash" >> ~/.bashrc && \
    echo "export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp" >> ~/.bashrc

# Команда по умолчанию при старте контейнера на дроне
CMD ["ros2", "launch", "install/share/gxf_isaac_camera_utils/launch/camera_split.launch.py"]

---
Как это собирается на твоем компе/ноутбуке/сборочном Jetson:
---

docker build -f Dockerfile.prod -t drone_firmware:latest .

---
Что происходит магии внутри Docker:
---

Он поднимает первый контейнер, копирует туда исходники, 
    тратит те самые 10 минут на компиляцию кода в папку /workspace/install.

Затем он открывает второй, абсолютно чистый образ.

Копирует из первого контейнера только результаты сборки (папку install).

Полностью уничтожает первый контейнер вместе со всеми твоими исходниками (src/) 
    и тяжелым кэшем компилятора (build/).

На выходе ты получаешь минимально возможный по размеру и максимально защищенный образ
drone_firmware:latest. Его ты и копируешь на остальные дроны. 

При его запуске на борту сразу же стартует пайплайн камеры,
не оставляя следов исходного кода на флешке дрона.

------
Что здесь относится к обычному, стандартному ROS2?
------

Импорты и структура (launch, launch_ros): 
    Классы ComposableNodeContainer и ComposableNode
    — это стандартные инструменты ROS2 для реализации концепции компонентов 
    (когда ноды запускаются не как отдельные тяжелые процессы OS, 
    а как динамические библиотеки .so внутри одного процесса-контейнера).

Контейнер (component_container_mt): 
    Это стандартный исполняемый файл ROS2 
    (многопоточный контейнер компонентов). 
    Его написали разработчики ROS2 (Open Robotics).
    Его задача — выделить общую оперативную память и потоки CPU для 
    загружаемых плагинов.

Перенаправление топиков (remappings): 
    Механизм, с помощью которого ROS2 связывает выходы одной ноды 
    со входами другой. 
    Строка ('image_raw', '/camera/pilot/image_color') — это чистый ROS2.    

    ---
    Нода argus_camera (Захват видео)
    ---

        Эта нода берет сырой поток с матрицы и аппаратно обрабатывает его. 
        Разработчики NVIDIA зашили внутрь ноды стандартные имена выходов: 
            image_raw 
                для самой картинки и 
            camera_info для метаданных калибровки.

    В launch-файле мы пишем:

    remappings=[
        ('image_raw', '/camera/pilot/image_color'),
        ('camera_info', '/camera/pilot/camera_info')
    ]


    ('image_raw', '/camera/pilot/image_color')

        Что происходит: 
            Мы говорим ноде: 
            «Вместо того чтобы публиковать цветную картинку в стандартный топик 
            image_raw, отправляй её в глобальный топик /camera/pilot/image_color».

            Зачем: Чтобы этот топик был явно именован как цветной поток для пилота, 
            и его не перепутали с другими камерами.

    ('camera_info', '/camera/pilot/camera_info')

        Что происходит: 
            Перенаправляем служебную информацию калибровки матрицы 
            из внутреннего имени camera_info в глобальный топик 
            /camera/pilot/camera_info.

    ---
    Нода format_converter (Перевод цвета в Ч/Б)
    ---

        Ей нужен входящий поток для обработки, и она создает исходящий поток.
        По умолчанию она ожидает входной поток на топике image_raw, 
        а результат выдает в топик image.

    В launch-файле мы пишем:

    remappings=[
        ('image_raw', '/camera/pilot/image_color'),
        ('image', '/camera/vins/image_mono')
    ]

    ('image_raw', '/camera/pilot/image_color')

        Что происходит: Это входное переназначение. 
        Мы заставляем конвертер слушать глобальный топик /camera/pilot/image_color
        (куда как раз пишет первая нода).

        Зачем: Так мы физически соединяем выход камеры со входом конвертера 
        прямо в памяти.

    ('image', '/camera/vins/image_mono')

        Что происходит: Это выходное переназначение. 
        Конвертер превращает цвет в монохром и хочет отправить это в топик image. 
        Мы перенаправляем этот выход в глобальный топик /camera/vins/image_mono.

        Зачем: Именно на этот топик теперь будет подписываться твоя система 
        визуальной одометрии (VINS-Mono).


Если бы мы не сделали ремаппинг, обе ноды попытались бы использовать топик 
image_raw 
для разных целей, что привело бы к хаосу в сети ROS2.


------
2. Что здесь относится конкретно к NVIDIA Isaac ROS?
------

NVIDIA взяла стандартные интерфейсы компонентов ROS2 и встроила в них
свою экосистему аппаратного ускорения. 
Конкретно к разработкам NVIDIA относятся:

Сами пакеты и плагины (package и plugin): 

    * isaac_ros_argus_camera и класс ArgusCameraNode 
        — это код NVIDIA. 
        Он внутри себя вызывает низкоуровневую библиотеку libargus 
        для прямого управления ISP Jetson.

    isaac_ros_image_proc и класс ImageFormatConverterNode 
    — это тоже код NVIDIA. Он выполняет конвертацию форматов на ядрах GPU.


Технология NITROS (NVIDIA Isaac Transport for ROS): 
    Это самое главное, чего не видно в коде launch-файла,
    но что происходит под капотом. 
    
    Когда ArgusCameraNode отправляет кадр в топик 
    /camera/pilot/image_color, 
    
    стандартный ROS2 должен был бы скопировать этот кадр в RAM, 
    сериализовать его и передать дальше. 
    
    Но плагины NVIDIA используют NITROS. 
        Они передают между собой не саму картинку, 
        а указатель на область памяти в GPU (NVMM). 
        
        Конвертер цвета берет этот указатель, 
        обрабатывает данные прямо в GPU и отдает дальше. 
        
        CPU при этом вообще не трогает пиксели кадра.

Ошибок в логах больше не будет.

1. Как DebayerNode получает цвета (Базовая физика)

Сенсор AR0234 накрыт цветовым фильтром Байера (Bayer filter). 
    Это значит, что каждый пиксель физически накрыт стеклышком определенного цвета:
    Красным (R), Зеленым (G) или Синим (B). 
    Обычно они идут в шахматном порядке: RGGB.

Когда сырой RAW-кадр попадает в узел DebayerNode на видеокарту, 
    алгоритм (на CUDA) точно знает эту шахматную расстановку.
    Он берет один красный пиксель, смотрит на соседние зеленые и синие, 
    и математически интерполирует их, собирая полноценный RGB-пиксель.

Итог: Так как физические фильтры на матрице никуда не делись, 
    алгоритм четко знает, где красный, а где зеленый свет. 
    Лист будет зеленым, а небо синим. Базовая цветопередача будет правильной.





2. Что мы действительно теряем без ISP (и почему я пугал синими листьями)
Матрица преобразования цветов (CCM) и Автоматический Баланс Белого (AWB) 
внутри ISP делают картинку идеальной при любом свете.

Без них ты столкнешься с тремя вещами:

Температурный сдвиг (Баланс белого): 
    Если ты вынесешь дрон на улицу в пасмурный день, 
    картинка может отдавать легкой синевой. 
    Если занесешь в комнату с желтыми лампами — она станет желтоватой. 
    Узел DebayerNode просто делает "тупую" математику и не пытается угадать, 
    какая сейчас погода.

"Плоские" цвета:
    Картинка может выглядеть не такой сочной (менее контрастной), 
    как на видео с DJI Mavic или GoPro.

Виньетирование (Lens Shading): 
    По самым краям кадра картинка может быть чуть-чуть темнее или уходить 
    в легкий фиолетовый оттенок из-за того, 
    что лучи света падают на края матрицы под углом. 
    ISP это исправляет математически, а V4L2 отдаст как есть.

Вот этот конкретный "выстрел в голову" всему конвейеру:

[component_container_mt-1] 2026-06-01 13:53:05.117 ERROR extensions/hawk/components/argus_camera.cpp@402: No cameras available



Давай разберем, что физически произошло в этом логе шаг за шагом:

    Инициализация графа: Контейнер component_container_mt-1 успешно стартует, загружает тяжелые библиотеки аппаратного ускорения NVIDIA (GXF, NITROS) и строит граф конвейера. В логах видно, как загружаются экстеншены: libgxf_multimedia.so, libgxf_cuda.so и прочие.

    Запрос к аппаратному уровню: Узел ArgusMonoNode (в логах он называется argus_camera) пытается инициализироваться и обращается к системному демону nvargus-daemon с командой: "Подключи меня к камере 0".

    Отказ (Следствие отсутствия .isp): Демон Argus, который при загрузке операционной системы не нашел файл калибровки .isp и профиль tegra-camera-platform для твоей матрицы, ранее уже заблокировал порт. Поэтому он отвечает узлу ROS 2: "У меня нет ни одной зарегистрированной камеры".

    Каскадный сбой (Агония фреймворка): Узел ROS 2 честно рапортует No cameras available. Поскольку камера является "корнем" (источником данных) всего графа, внутренний планировщик NVIDIA (GXF) не может запуститься. Все последующие пугающие строки в твоем логе — Failed to start entity, GXF_FAILURE, Graph interrupt failed, Deactivation failed — это просто каскадное падение фреймворка, который пытается экстренно убить процессы, так и не дождавшись ни одного байта данных.

    Этот лог — финальное техническое доказательство нашего расследования. Узел ArgusMonoNode абсолютно слеп к камере без проприетарных конфигов. Тебе нужно удалить этот лаунч-файл и использовать тот, что построен вокруг узла V4L2, чтобы забрать сырые кадры в обход закрытого демона.

import launch
from launch_ros.actions import ComposableNodeContainer
from launch_ros.descriptions import ComposableNode

def generate_launch_description():
    # 1. Захват через стандартный V4L2 (сохраняет кадр в RAM, передает в ROS)
    v4l2_node = ComposableNode(
        name='v4l2_camera',
        package='v4l2_camera',
        plugin='v4l2_camera::V4L2Camera',
        parameters=[{
            'video_device': '/dev/video0',
            'image_size': [1920, 1200],
            # Важно: для AR0234 укажите правильный формат пикселей
            # Обычно это 'YUYV' или сырой байер ('RGGB', 'BGGR' и т.д.)
            # 'pixel_format': 'RGGB' 
        }],
        remappings=[
            ('image_raw', '/camera/raw_bayer')
        ]
    )

    # 2. Аппаратный дебайеринг на GPU/VIC
    # Узел принимает стандартное ROS-сообщение, переносит его в VRAM и обрабатывает аппаратно
    debayer_node = ComposableNode(
        name='debayer_node',
        package='isaac_ros_image_proc',
        plugin='nvidia::isaac_ros::image_proc::DebayerNode',
        remappings=[
            ('image_raw', '/camera/raw_bayer'),
            ('image', '/camera/pilot/image_color')
        ]
    )

    # 3. Аппаратная конвертация на GPU (подготовка mono8 для визуальной одометрии)
    converter_node = ComposableNode(
        name='format_converter',
        package='isaac_ros_image_proc',
        plugin='nvidia::isaac_ros::image_proc::ImageFormatConverterNode',
        parameters=[{
            'encoding_desired': 'mono8',
        }],
        remappings=[
            ('image_raw', '/camera/pilot/image_color'),
            ('image', '/camera/vins/image_mono')
        ]
    )

    # 4. Единый контейнер
    container = ComposableNodeContainer(
        name='camera_container',
        namespace='',
        package='rclcpp_components',
        executable='component_container_mt',
        composable_node_descriptions=[v4l2_node, debayer_node, converter_node],
        output='screen'
    )

    return launch.LaunchDescription([container])





Как это будет работать "под капотом":
Драйвер камеры читает кадр 1920x1200 в оперативную память (RAM).

Узел v4l2_camera публикует стандартное ROS-сообщение sensor_msgs/Image. 
    На этом этапе задействуется процессор ARM.

Узел DebayerNode (благодаря NITROS) перехватывает это сообщение, 
    аллоцирует буфер в памяти GPU и переносит туда кадр.

Выполняется аппаратный дебайеринг.

Узел ImageFormatConverterNode берет уже готовый GPU-буфер 
    (Zero-Copy передача между узлами Isaac) и аппаратно конвертирует его в mono8.

Результат отдается для VINS-Mono.

Полная совместимость по сообщениям
Для внешнего мира (твоих самописных нод или VINS-Mono) нода Isaac ROS 
выглядит как совершенно обычный узел ROS 2. 

Она публикует и подписывается на стандартные типы данных, 

например sensor_msgs/msg/Image или sensor_msgs/msg/CameraInfo.
Твой VINS-Mono даже не поймет, что картинка пришла из какой-то 
особенной нейросетевой или аппаратно-ускоренной ноды. 

Он просто подпишется на топик и начнет работать.

Сырой цветной Bayer без ISP всегда выглядит как шумный кислотный трип
с диким зелено-малиновым оттенком.

Чтобы получить красивую, гладкую картинку, привычную глазу 
(как с веб-камеры или смартфона), 
нужен ISP (Image Signal Processor). 


Он делает огромную вычислительную работу за кадром:

AEC (Автоэкспозиция):
Динамически подстраивает яркость, 
чтобы окна не были белыми пятнами, а темные углы — черными дырами.

AWB (Автоматический баланс белого): 
    Выравнивает цвета, чтобы белый цвет оставался белым при разном освещении (иначе мы видим тот самый кислотный трип).

Гамма-коррекция:
    Делает тени и свет более контрастными. 
    Сейчас твоя картинка выглядит очень плоской и серой именно из-за того,
    что кривая гаммы линейная.

Denoising (Шумоподавление):
    Сглаживает то самое зерно, которое сейчас обильно сыпет по всему кадру.


NVIDIA Argus
GStreamer-плагин nvarguscamerasrc

Как задействовать ISP на Orin Nano?
Jetson имеет на борту очень мощный аппаратный ISP, 
но мы его обошли. Команда v4l2-ctl читает данные напрямую 
с шины CSI/MIPI на самом низком уровне.

Чтобы картинка стала "нормальной", 
нужно пустить поток через прослойку NVIDIA Argus.
Обычно это делается не через прямое чтение буфера в Python, 
а через GStreamer-плагин nvarguscamerasrc. 

Этот плагин забирает сырой Bayer, прогоняет его через железный 
ISP Джетсона и выдает готовый, красивый H.264/H.265 или JPEG. 
Для идеальной работы этого конвейера также нужны калибровочные файлы 
(tuning files) от Arducam, чтобы ISP Jetson'а понимал специфику матрицы AR0234.

!!! Docker
Пакеты Isaac ROS официально заточены именно под эту связку (и под JetPack 5/6). 
Они поставляются в виде готовых Docker-контейнеров от NVIDIA, 
чтобы не засорять хост-систему зависимостями, 
хотя можно собрать их и "наживую", если умело управлять путями CUDA.

И еще бонус: 
    поскольку пакеты NVIDIA написаны на плюсах с жесткой оптимизацией,
    тебе не придется терпеть медленный Python в production-пайплайне.

Фишка Isaac ROS в технологии NITROS (NVIDIA Isaac Transport for ROS).
Если две ноды Isaac ROS общаются между собой 
    (например, нода захвата с камеры передает кадр ноде кодирования видео H.265),
    они вообще не копируют данные в оперативную память.
    Они просто передают друг другу указатель на участок видеопамяти (NVMM) в GPU.
    Это дает нулевую задержку.

Когда же кадр нужно отдать в твою обычную ноду
    (например, в VINS-Mono, который крутится на CPU),
    Isaac ROS прозрачно "выгружает" картинку из видеопамяти в стандартный
    ROS-сообщение и отдает тебе. 
    Да, тут происходит одно копирование в RAM, 
    но это неизбежно для алгоритмов на процессоре.

Алгоритмам (VINS) 
    нужен сырой, темный, стабильный монохром без скачков яркости.

Пилоту (FPV) 
    нужна полноцветная, светлая картинка, 
    где автоэкспозиция мгновенно отрабатывает вылет из леса на яркое солнце.


Развести эти потоки можно двумя путями:

Программный дебайер (ROS2): 
    Мы берем наш текущий сырой поток.

    Одна его копия уходит напрямую в VINS.

    Вторая копия отправляется в специальную ноду

        (например, image_proc или самописную на CUDA),
        которая программно превращает Bayer в цвет,
        накидывает гамму и жмет в H.265 для пилота. 
        Минус — нагрузка на GPU/CPU.

Двойной вывод (Argus C++ API): 
    Использовать низкоуровневый API NVIDIA Argus. 
    Он позволяет запросить у железа Джетсона одновременно два потока с одной камеры:
    один буфер отдавать абсолютно сырым (Sensor-Direct),
    а второй буфер пропускать через ISP для пилота. 
    
    Это высший пилотаж, дает идеальную задержку и нулевую нагрузку на процессор.

Для видеолинка пилоту с этой AR0234 
    ты планируешь жать поток в H.264/H.265 прямо через ROS-ноду и слать по сети, 
    или этот поток должен будет подхватываться отдельным стеком (например, OpenHD)?


Если запустить аппаратный nvarguscamerasrc, 
    он "захватит" камеру, включит автоэкспозицию и выдаст красивую картинку, 
    но SLAM от таких скачков освещенности сойдет с ума. 
    
    Если брать сырой кадр (как мы сделали), 
        пилот будет видеть плоскую серую мглу.
