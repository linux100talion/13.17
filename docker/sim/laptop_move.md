# Переезд на ноутбук с RTX 4050 Max-Q — чек-лист и что там меняется

Стенд до сих пор жил на GCE-боксе **без GPU** (ветка CPU-оверрайда, `CPU=1`,
llvmpipe, RTF ≈ 0.07). Цель переезда — реальное время в Gazebo и **живой пульт**
вместо скриптованного пилота. Здесь то, что понадобится в первый час на новой
машине, и то, что от смены RTF ломается не сразу и молча.

---

## 1. Поднять стенд (по порядку)

```bash
# хост: драйвер NVIDIA + docker + nvidia-container-toolkit (проверка)
nvidia-smi
docker run --rm --gpus all nvidia/cuda:12.2.2-base-ubuntu22.04 nvidia-smi

# Каталоги выбираются свободно — ниже они подставляются через переменные.
# REPO может быть где угодно (не обязательно /root), VINS_SRC — тоже.
REPO=~/13.17
VINS_SRC=~/VINS-MONO-ROS2

git clone -b nn2_c3_control2 https://github.com/linux100talion/13.17 "$REPO"
git clone --branch 1317_debug https://github.com/linux100talion/VINS-MONO-ROS2 \
          "$VINS_SRC"                   # ⚠️ форк живёт ВНЕ репы, монтируется bind-mount'ом

cd "$REPO/docker/sim"
# Путь к форку compose берёт из VINS_SRC (дефолт — /root/VINS-MONO-ROS2, раскладка
# GCE-бокса). Если форк лежит не там — записать путь в docker/sim/.env (не коммитится):
echo "VINS_SRC=$VINS_SRC" > .env
docker compose config | grep -A2 vins_oss   # проверить, что путь подставился

make host-setup     # xhost + v4l2loopback (/dev/rawbayer), нужен sudo
echo "CUDA_ARCH_BIN=8.9" >> .env   # RTX 4050 Max-Q (AD107M, Ada) = 8.9; одна арка вместо четырёх
make build          # долго: SITL + Gazebo + OpenCV с CUDA из исходников
#   Дефолт ("7.5;8.0;8.6;8.9", RTX 20/30/40) собирается и без правок, но вчетверо
#   дольше нужного. `make build` аргументы НЕ пробрасывает — арка задаётся только
#   через .env (compose подставляет её в build.args образа nav).
make up && make wait
make sitl-cal       # ОДНОРАЗОВО после первого подъёма/после make clean
make gui            # окно Gazebo (на GPU-ноуте; GCE-бокс жил headless)
```

**Окно Gazebo (`make gui`)**: сервер как шёл headless (`gz sim -s`), так и идёт —
окно это ОТДЕЛЬНЫЙ клиент `gz sim -g` в контейнере (X11 проброшен в compose,
`xhost` делает `host-setup`). Клиент — чистый зритель: на прогон/bag не влияет,
дисциплину не нарушает; НО кнопки play/pause в окне жмут НАСТОЯЩИЙ сервер — не
трогать во время прогона. После `restart-all`/`fresh-start` сервер новый — окно
закрыть и снова `make gui`. Лог клиента: `output/gz_gui.log`.

**Плавность окна ≠ скорость симуляции.** RTF смотреть в панели World stats (низ
справа): RTF ≈ 1.0 = симуляция идёт в реальном времени, даже если окно дёргается.
На гибридном ноуте X-сервер сидит на Intel iGPU → клиенту нужен `/dev/dri`
(проброшен в compose), иначе Mesa падает на llvmpipe (софт-рендер, ~150% CPU,
слайд-шоу; в `gz_gui.log` — `failed to open /dev/dri/cardN`). Сервер и камера
дрона рендерятся на NVIDIA (EGL) независимо от окна.

**Вид с камеры дрона** — три окна на выбор, все чистые зрители (стек не трогают):
1. В окне Gazebo (`make gui`): панель **«Камера дрона»** уже пристыкована справа
   (плагин ImageDisplay на `/camera/image_raw`, конфиг `worlds/gui_fpv.config` —
   в меню ⋮ его искать не надо). Это ИДЕАЛЬНЫЙ рендер сенсора — до байеризатора
   и дебайера.
2. `make fpv` — боевой поток оператора: `openhd_streamer` шлёт H.264 на UDP :5600
   (nav в host-сети → порт виден на ноуте), 640×360 с рамками NN1/меткой NN2.
   Именно это увидит оператор в OpenHD на реальном борту. Смотрится GStreamer'ом
   с хоста; поток идёт всегда, окно можно открывать/закрывать когда угодно.
3. `docker exec -d p1317_simulator bash -c "ros2 run rqt_image_view rqt_image_view /image_color"`
   — то, что реально ПОЛУЧАЮТ нейросети после цепочки bayer→CUDA-дебайер (полный
   кадр, без оверлея). Для `/image_mono` — вход VINS. Контейнер simulator: в nav
   нет ни X11, ни rqt.

⚠️ **Нужен нативный Docker Engine, не Docker Desktop.** Desktop под Linux крутит
контейнеры в виртуалке, а стенду это ломает всё сразу: `runtime: nvidia` там не
поддерживается, `network_mode: host` станет хостом ВМ, а `/dev/rawbayer` — модуль
ядра ХОСТА, которого ВМ не видит. Проверка — `docker context ls` (активным должен
быть `default` → `/var/run/docker.sock`) и `systemctl is-active docker`.

**`CPU=1` больше не нужен** — это флаг GPU-less бокса. Со всеми таргетами идём без него.

Первый прогон-проверка (он же образец дисциплины: атомарно, целиком):

```bash
NAME=L0 bash "$REPO/src/lab/calib_run.sh"
```

## 2. Что меняется от RTF 0.07 → ~1 (грабли, каждая уже кусалась)

**Камеру можно вернуть на 1280×720.** CPU-оверрайд занижал её до 320×180
(`CAMERA_W/H` в `docker-compose.cpu.yml`), llvmpipe больше не тянул; вся кампания
`YW/IG/BW` летала на 960×540 (`RES=960x540` — это и есть `CAMERA_W/H`, дефолт
`calib_run.sh`). Под 1280×720 посчитаны интринсики `sim.yaml`
(`fx=fy=640, cx=640, cy=360`), так что на GPU-боксе VINS впервые поедет на своём
расчётном разрешении — но менять разрешение и сравнивать с кампанией одновременно
нельзя. Порядок: сначала переснять базу (3 прогона конфигом `YW3s`) на том
разрешении, на котором дальше летим, и только потом мерить новое против неё.

**Частота кадров вырастет — а окна и гейны считались в КАДРАХ.** `yaw_smooth` — окно
медианы в кадрах, `arm_frames` — кадры, `ipm_win` — секунды (это ок). Сглаживание курса
уже ловили на этом: оно ведёт себя как ВРЕМЕННОЕ окно, а не как «5 кадров», и при смене
fps эквивалент меняется. Проверить `yaw_smooth` и всё, что считает кадры, первой же
серией.

**Бюджеты в sim-секундах переносятся без правок** (`SIM_BUDGET`, `*_BUDGET`), а вот
wall-таймауты — нет: `ARM_WALL_CAP` (дефолт 1200 с в `arm.sh`) ставился с запасом под
RTF 0.07 и на новой машине просто избыточен, но `make wait` (5 мин) и таймаут ожидания `/dev/rawbayer` (60 с) рассчитаны
на медленный бокс — если что-то падает по таймауту, смотреть туда.

**Диск и видео.** При RTF ≈ 1 сырой bag с `/image_color` растёт в разы за то же
sim-время. `hover_series.sh` потрошит бэги сразу после прогона (`STRIP=1`) — не
отключать. `make logs` и `df -h` держать под рукой.

**IMU-патчи VINS остаются нужны** (`timesync_mode:=NONE` + skip-патч в
`estimator_node.cpp`, ветка `1317_debug`): причина в SITL-протоколе, а не в скорости
машины. Но `/clock` ~155 Гц против 250 Гц IMU на быстрой машине даст другую картину
дубликатов — если в логе VINS снова появится `imu message in disorder`, начинать
разбор оттуда.

## 3. Живой пульт: петля подтверждена, путь — joy МИМО FCU (реализован)

⚠️ **ГЛАВНАЯ ЗАСАДА — НЕ гипотеза, а устройство ArduPilot.** `RC_CHANNELS_OVERRIDE`
поканально ЗАМЕЩАЕТ `radio_in`, и телеметрия `RC_CHANNELS` (→ `/mavros/rc/in`) отдаёт
именно эти значения; пред-override RC в MAVLink не существует. Пока нода пишет
`/mavros/rc/override` (ch1..4), в `rc/in` ch1..4 — эхо её же команды, а физические
стики не видны ВООБЩЕ: в assist — самораскачка («борт сам себя разгоняет»), в
MANUAL-seize — защёлка (замораживается последняя команда, стики её не сдвинут).
Параметром не лечится (`RC_OPTIONS` «ignore overrides» убил бы наш выход). Сигнатура
для проверки на стенде: ch6 в `rc/in` ходит за тумблером (мы его не оверрайдим),
ch1..4 за стиками — НЕТ. Отсюда же: старые варианты проброса (MAVProxy joystick /
мостик joy→`RC_CHANNELS_OVERRIDE`) мертвы — оба шлют стики В FCU (эхо остаётся) и
дерутся с нашим override на тех же каналах.

**Решение (в коде): намерение пилота идёт МИМО FCU.** TX12 в режиме USB-джойстика →
`joy_linux_node` → `/joy` → `JoyPilot`. Нода — единственный писатель override.

| слой | файл | роль |
|---|---|---|
| источник | `control_pkg/infrastructure/ros_pilot.py` → `JoyPilot` | читает `/joy` (мимо FCU); оси = каналы микшера EdgeTX: axes[0..3] = стики, axes[5] = CH6 тумблер (порог 0.5 = зеркало «1700») |
| легаси (⚠️ петля) | тот же файл → `RosPilot` | `/mavros/rc/in` — только когда нода НЕ оверрайдит ch1..4 |
| замена на время сима | тот же файл → `ScriptedPilot` | детерминированный профиль стиков по sim-времени |
| намерение | `domain/control/trajectory.py` → `RcTransmitter` | стик → цель скорости (нормировка `pilot_deadzone=30`, `pilot_full=400`, знаки `pilot_*_sign`) |
| выход | `infrastructure/mavros_actuator.py` | `/mavros/rc/override`, каналы 1..4 |

Обвязка: `ros-humble-joy-linux` + `jstest` в образе `nav` (нужен `make build`),
`/dev/input` проброшен каталогом + cgroup-правило major 13 (hotplug: пульт можно
втыкать после старта; изменение compose требует `fresh-start`). `joy_linux_node`
поднимает `bootstrap_arch2.sh` сам при `BS_PILOT=joy` (устройство — `JOY_DEV`,
default `/dev/input/js0`; лог `output/joy.log`).

**Первый прогон живого пульта (на земле, до полёта):**

1. Пульт в USB-режим джойстика (при втыкании USB выбрать «USB Joystick (HID)»),
   в микшере модели: CH1..4 = AETR, CH6 = тумблер (SC/SD). Хост: `ls /dev/input/js*`.
2. Сверка одной командой (стек поднимать не нужно, только контейнер):
   `docker exec -it p1317_nav bash /lab/joy_check.sh` — поднимает joy_linux_node и
   живьём печатает СТИКИ ГЛАЗАМИ НОДЫ (то же ядро `joy_sticks()`, что у JoyPilot):
   PWM всех четырёх осей + MANUAL/AUTO. Если устройства нет — сырой HID смотреть
   `jstest /dev/input/js0`.
3. Знаки — ВЫВЕРЕНЫ живыми полётами (assisted/MANUAL, 2026-08-16): в EdgeTX-HID
   зеркальны нашей RC-конвенции roll, yaw И throttle; «прямой» только pitch —
   потому что провод RC2 сам инвертирован (стик от себя → HID минус → PWM 1300 =
   вперёд). Зашито в `JOY_SIGNS_DEFAULT` (`ros_pilot.py`), переопределение —
   `BS_JOY_SIGNS="r,p,t,y"` (`--joy-signs`). Каждый знак подтверждался только
   тем полётом, где ось РЕАЛЬНО дошла до провода: pitch — вторым (в первом CH2
   отсутствовал в микшере — EdgeTX шлёт 0 по каналу без микса; CH6/SC — та же
   история), throttle — первым полётом с passthrough (до него ось игнорировалась,
   и «прямой» был непроверенным предположением). Уроки: мёртвая ось в bag =
   дырка в микшере пульта, не бага ноды; знак не считается выверенным, пока ось
   не отработала в воздухе. Сверять `joy_check.sh` (печатает PWM уже С боевыми
   знаками — «вправо → 1900», «газ вверх → 1900» буквально). `pilot_pitch_sign = -1.0` остаётся парным к `_PITCH_RC_SIGN` в
   `ControlStack` (вместе — pass-through); зеркальный знак уже стоил разбора
   (`6841c58`). Газ: РАБОТАЕТ и в assisted, и в MANUAL — через `ThrottleLatch`
   (газ заперт, пока стик не побывал в центре: вход в режим с отклонённым газом
   безопасен). Стик вне центра = вертикальная скорость (ALT_HOLD), отпустил =
   держит текущую высоту. Тумблер SC — ТРЁХПОЗИЦИОННЫЙ СЕЛЕКТОР (токен `pilot<t>`
   в BS_MISSION, только живой пилот):
   - **вверх (−1)** — наш стабилизатор (BS_STAB, напр. DpHoldM): стики = намерение,
     демпфер держит; при щелчке опоры пересеиваются от текущей точки.
     ⚠️ Намерение на roll/pitch проходит ТОЛЬКО при `BS_*_RATE_CMD_GAIN > 0`
     (м/с при полном стике); при дефолте 0 демпфер целит нулевую скорость и
     СТИКИ ИГНОРИРУЕТ (полёт 2026-08-17: полный «на себя» не тормозил разгон —
     пилот пассажир до fence). Живыми остаются газ (латч) и yaw;
   - **центр (0)** — чистый ALT_HOLD: стабилизаторов нет, стики = наклоны;
   - **вниз (+1)** — MANUAL: Арбитр отдаёт пилоту сырые стики, миссия отстранена.
   Сверка направлений: joy_check печатает STAB/ALTHOLD/MANUAL; если верх/низ
   поменяны местами — правится weight в миксе CH6, не код. Выверенная конфигурация
   пульта (наземная сверка 2026-08-17): сырой SC в EdgeTX даёт вверх = −100, и
   HID зеркалит CH6 так же, как оси → в миксе CH6 нужен weight **−100** (числом,
   не GVAR — G1 может жить своей жизнью): канал вверх = +100 → HID −1 = STAB,
   вниз = −100 → HID +1 = MANUAL. Монитор каналов пульта показывает канал ДО
   HID-зеркала — сверять по joy_check.
   ⚠️ **Начальное состояние осей**: joy_linux_node по умолчанию ИГНОРИРУЕТ
   JS_EVENT_INIT — тумблер/стик, выставленный ДО старта ноды, публикуется как
   0.00 до первого движения. Полёт 2026-08-17: CH6 вверх выставлен до взлёта →
   нода весь полёт видела «центр» → чистый ALT_HOLD (A4-дрейф → fence → LAND)
   вместо нашего стабилизатора; по бэгу это выглядит как «ось без единого
   события» при живых остальных осях. Фикс: `-p default_trig_val:=true` в
   запуске joy_linux_node (`bootstrap_arch2.sh`, `joy_check.sh`) — первое
   сообщение `/joy` сразу несёт фактическое положение.

Полетать с селектором (гейны DpHoldM — из tune.md, конфиг P2s):
```bash

  BS_ARM_BUDGET=80 BS_CLIMB_BUDGET=120 BS_FENCE=25 BS_MODE_BUDGET=80 \
  BS_IPM_DEROT=1.0 BS_IPM_WIN=0.5 BS_IPM_WZ_TAU=2.0 BS_LAND_BUDGET=180 \
  BS_PITCH_OSIGN=1 BS_PITCH_RATE_KI=30 BS_PITCH_RATE_KP=30 \
  BS_PITCH_RATE_CMD_GAIN=5 BS_ROLL_RATE_CMD_GAIN=5 \
  BS_ROLL_IMAX=150 BS_ROLL_OSIGN=1 BS_ROLL_RATE_KI=30 BS_ROLL_RATE_KP=30 \
  BS_SLEW=300 BS_THROTTLE_CLIMB=1800 \
  BS_YAW_ARM_FRAMES=5 BS_YAW_KD=6 BS_YAW_KI=0 BS_YAW_KP=20 BS_YAW_LEAK=8 \
  BS_YAW_MAX_RATE=100 BS_YAW_SMOOTH=5 \
  TOPICS_EXTRA="/joy /model/iris_cam/odometry" GDRIVE_UP=0 MP4=1 \
  bash src/lab/capture_scene.sh 960x540 bootstrap_arch2
```
⚠️ `BS_PITCH_RATE_KP=30` (был 100): свип PTkp30/50/100 (hover40, 2026-08-18) —
kp=100 звенел (26 смен знака/мин, качели ±1.5-2 м/с), kp=30 выиграл по всем
метрикам (СКО vfwd 0.45 против 0.61-1.02, ср|PWM| 20 против 53-69, уход 4.5 м).
Симметрично крену, у которого 30 стояло всегда. Плюс с этого дня по умолчанию
включён комплементарный фильтр скорости IPM (`ipm_vel_tau=0.4` в config):
провалы кадров мостятся прогнозом наклона тяги, ipm_ok в воздухе 100%.
⚠️ `BS_PITCH_RATE_KI=30` (был 100) и `CMD_GAIN=5` (был 2) — по жалобам живого
пилота (freefly 2026-08-18): ki=100 на лагающем измерении раскачивал тангаж и
«запоминал» торможение (интегратор ±120 PWM разматывается ~1.5 с против стика),
а cmd_gain=2 значил «полный стик = всего 2 м/с» — при крейсерских 4-7 м/с
демпфер постоянно тормозил против пилота. Контроль ki=30 (PTki30_bag): звон
3 смены/мин (лучший), насыщений 0%. Цена: hands-off снос чуть больше (I-член
компенсировал постоянную силу рампы) — в пилотируемых режимах размен верный,
для автономного hover можно вернуть BS_PITCH_RATE_KI=100.
⚠️ `BS_YAW_RATE_FULL` — общий темп рыскания, °/с при полном стике (дефолт
28.65 = темп GzHold, для FPV вяло). Ручка выведена наружу 2026-08-18; для
живого пилота ставить 60 (потолок правдоподобия BS_YAW_MAX_RATE=100 оставляет
запас — поднимать темп выше ~80 только вместе с потолком).
⚠️ `BS_YAW_KP` — жёсткость «пружины» курс-холда: 20 = жёсткий холд (нужен
автономным yaw_l/r-токенам с добором угла), 6 = мягкая пружина, 0 = чистый
rate-демпфер (стик = темп, отпустил = остался; исходный победитель свипа).
Живому пилоту в freefly ставить 0: с kp=20 пружина сопротивляется развороту
быстрее уставки и оттягивает курс после отпускания стика (жалоба пилота
2026-08-18). Цена kp=0 — медленный дрейф курса без рук (~3-4° за десятки
секунд, утечка ограничивает). ⚠️ СО СТАНЦИЕЙ (BS_*_POS_KP) ставить kp=6:
дрейф курса при kp=0 заставляет станцию перезахватывать точку каждые ~17°
(путь в body-осях) — точка тихо едет со сносом (freefly 2026-08-18: 15 м
увода за 27 с hands-off).
⚠️ `BS_PITCH_POS_KP/BS_ROLL_POS_KP` + `BS_*_POS_VMAX` — СТАНЦИЯ-КИПИНГ:
стик в центре → захват точки по накопленному пути IPM и цель скорости
pos_kp·(точка−путь), кламп ±vmax; стик живой → точка отпущена (пульт всегда
главный, как LOITER). Рабочие числа: 0.15 / 0.7 — прогон POSKP2: снос выходит
на ПЛАТО (~9.5 м на злой рампе 30+ с) вместо бесконечного ползания, звона нет
(3 смены/мин). ⚠️ pos_kp=0.5 ЗВЕНИТ (POSKP: предельный цикл ±2-4 м/с, период
11 с, насыщение 14%) — внешний контур обязан быть в разы медленнее
внутреннего (τ скоростного контура ~5 с из-за занижения измерения ×0.5-0.6).
Затягивать станцию — только после улучшения оценщика (optical-flow → EKF).

`pilot60` = 60 сим-сек живого пилотирования между взлётом и посадкой; селектор
щёлкается на лету сколько угодно раз. **`pilot` БЕЗ числа** (`BS_MISSION=
"climb3,pilot,land"`) = летаем БЕССРОЧНО; закончил — из второго терминала
`make pilot-done` (в `docker/sim/`; шлёт `/mission/pilot_done` в ноду) → миссия
идёт дальше (land, стоп bag, кадры/mp4). Ctrl+C на capture_scene — только
аварийно: он убивает секвенсор целиком, без посадки и без сборки артефактов.

**`freefly` — свободный полёт, миссия-одиночка** (`BS_MISSION="freefly"`, другие
токены рядом — ошибка). Борт просто спавнится, весь цикл — руками с пульта:
арм руддером (газ вниз + yaw вправо ~2 с), взлёт газом, полёт, посадка, дизарм
руддером (газ вниз + yaw влево) — дизарм и завершает миссию (bag/кадры собираются
как обычно). Газ СЫРОЙ (без защёлки и AltHold — пилот владеет вертикалью с нулевой
секунды), **геозабор игнорируется**, селектор CH6 после арма работает как в
`pilot`. До арма все оси сырые независимо от тумблера (иначе руддер-арм не
пробить через демпферы). ⚠️ Армить с тумблером вверх/в центре: в MANUAL (+1)
газ идёт через защёлку Арбитра. Команда — та же P2s, только
`BS_MISSION="freefly"` (бюджеты climb/land не участвуют).

Боевой сценарий пре-VINS собран: `BS_PILOT=joy` + `control_mode=flow_assist` (демпфер
крена+курса, тангаж — сырой стик) либо `BS_STAB=DpRollHold+DpYawHold` с миссией.
Завершение живого полёта: тумблер MANUAL → посадка руками (Control-фаза без
`BS_EXCITE_MAX` не ограничена по времени — это контракт живого пилота).

### Штатный LOITER-на-VINS (серия LV)

Канонический ArduPilot-маршрут «VINS → vision_pose → EK3 extnav → Loiter»: позицию
держит контроллер САМОГО полётника, наш override для него — стики пилота (в Loiter
стик = уставка скорости). Оракул и фолбэк для `VinsHold`: тот же VINS, держит
прошивка. ⚠️ Loiter'у нужна не GPS, а ПОЗИЦИОННАЯ ОЦЕНКА на FCU — без GPS она
появляется только ПОСЛЕ init VINS и перевода EK3 на extnav, поэтому взлёт всегда
в ALT_HOLD, а вход в LOITER гейтится: `extnav_ready` (очередь `EK3_SRC1_*` пар
3→6 пройдена) + свежий VINS + в воздухе (>1.5 м). Гейт закрыт → честный ALT_HOLD.

⚠️ **Пререквизит: `VISO_TYPE 1` в `config/sitl-extra.parm` (раскомментировать).**
LV — vision-серия: без VISO_TYPE полётник игнорирует vision_pose/vision_speed,
EKF после GPS-kill остаётся без позиции и отвечает «Mode change to Loiter failed:
requires position» (урок LV1_loiter: вся цепочка до гейта отработала, LOITER —
REFUSED; заодно за 80 с попыток z-оценка EKF уехала и AltHold притёр борт к
земле). После серии вернуть назад — с VISO_TYPE=1 любой прогон БЕЗ vision-фида
перестаёт армиться («VisOdom: not healthy», см. комментарий в parm).

Две ручки (обе требуют vision-фида — `BS_VISION_VEL=1 BS_VISION_POSE_SRC=extern`,
профиль GPS-denied серии):

- **Токен `loiter<t>`** (scripted, атомарная метрика): стабилизированный hover до
  открытия гейта (бюджет `BS_LOITER_GATE_BUDGET`, дефолт 60 с; не открылся —
  LOITER_SKIP, миссия продолжается) → LOITER t сек со стиками в центре (держит
  FCU) → дальше по плану. FCU выпал из LOITER сам (failsafe) — уважаем и выходим
  (LOITER_EJECT); VINS протух — LOITER_STALE. Эталонная команда серии (sk-токены
  дают параллакс для init VINS, hover — спокойную фазу для смены источников):

  ```bash
  REPO=$(git rev-parse --show-toplevel)
  cd $REPO && setsid nohup env NAME=LV_loiter GDRIVE_UP=1 MP4=1 \
    BS_PILOT=scripted BS_STAB=DpHoldM BS_HANDOVER_VINS=1 BS_VINS_MIN=300 \
    BS_MISSION="climb3,sk_fwd3,sk_fwd3,hover10,loiter40,land" \
    BS_VISION_VEL=1 BS_VISION_POSE_SRC=extern BS_GPS_DISABLE=1 \
    BS_THROTTLE_CLIMB=1800 BS_MODE_BUDGET=80 BS_ARM_BUDGET=80 \
    BS_CLIMB_BUDGET=120 BS_LAND_BUDGET=180 BS_SLEW=300 \
    TOPICS_EXTRA="/model/iris_cam/odometry /odometry" \
    bash src/lab/calib_run.sh > docker/sim/output/LV_loiter.log 2>&1 < /dev/null & disown
  ```

  Успех = `ИТОГ: LOITER_DONE`. Бейслайн для сравнения — тот же прогон с
  `hover40` вместо `loiter40` (то же окно, но держит `VinsHold` после хэндовера);
  метрика удержания — по истинной позе `/model/iris_cam/odometry` в обоих bag.
  Пара `EK3_SRC1_*→6` в mission-планах уходит ТОЛЬКО в hover/loiter-фазе
  (гейт `_calm_phase` в ноде — урок LV2: свап посреди sk-манёвра = разгон-улёт
  за fence за 3.5 с; в freefly гейта фазы нет — щёлкать в спокойном ховере).

  ⚠️ **`BS_VINS_MIN=300` — обязательная часть профиля** (дефолт 40 для
  VinsHold-под-манёвром мал). Урок LV6 против LV5/LV7: свап на VINS возрастом
  1.5 с от init (40 odom) посреди sk-манёвра дал ускоряющийся разгон до fence
  при ЧЕСТНОЙ опоре (поза 41.16 против истинных 41.0 м, курс ±3°) — скорость/
  масштаб свежего VIO ещё плывут; свап на зрелом VINS (300+ odom) чист даже
  посреди манёвра (LV5). Дефолт `vins_min` не переигран (n=1, дисциплина
  tune.md) — для LV-профиля ручка обязательна.

  **Результаты серии LV (2026-08-19, прогоны LV5/LV7, окно 40 с по gt):**

  | | Loiter полётника (LV5, LOITER_DONE) | VinsHold (LV7, MISSION_DONE) |
  |---|---|---|
  | ср. отклонение от центра | 0.85 м (СКО 0.44) | **0.07 м** (СКО 0.05) |
  | макс. отклонение | 1.69 м | 0.24 м |
  | размах x×y | 2.1 × 3.3 м | 0.19 × 0.29 м |
  | дрейф начало→конец | 0.30 м | 0.11 м |
  | размах z | 0.84 м (alt держит FCU) | 0.62 м (наш AltHold-контур) |

  Оба — на чистом VINS (GPS заглушен в ховере). Разница ×10 — это не «плохой
  Loiter»: он честно держит ОЦЕНКУ EKF, а та блуждает относительно истины
  (инновации 1.6/2.5 м, серия №8); VinsHold ест сырую VINS-позу напрямую,
  которая в симе почти идеальна. На реальном борте с шумным VINS зазор
  сожмётся: EKF сглаживает, прямой путь наследует шум опоры как есть.
  Хронология отказов серии (каждый — закоммиченный фикс): LV1 VISO_TYPE выкл →
  REFUSED; LV2 свап EKF-источников на манёвре → FENCE (→ _calm_phase);
  LV3 композит DpHoldM обезвреживал VinsHold → FENCE (→ порядок keep+[vins]);
  LV4 арм до захвата позиции EKF, гонка бута → REFUSED (→ шаг ekf_warmup);
  LV6 свап на незрелый VINS → FENCE (→ BS_VINS_MIN=300).
  `BS_GPS_DISABLE=1` — чтобы LOITER жил на VINS, а не на GPS; первый прогон можно
  сделать БЕЗ него (инкремент: сперва latch/удержание, потом GPS-denied).

- **Freefly-селектор `BS_FF_LOITER=1`** (живой пилот): центр CH6 = штатный LOITER
  вместо чистого ALT_HOLD. **Доказан в полёте 2026-08-20** (шестой прогон
  пилотной серии, W10, GPS заглушен): латч < 2.5 с с первого set_mode, 0 отказов,
  0 EKF-событий, hands-off сразу после латча — ср. отклонение **0.12 м**
  (макс 0.50) за 34 с. Цена — пять вскрытых слоёв: VISO_TYPE в eeprom → арм до
  aiding (ekf_warmup) → зрелость VINS для свапа → якорение кадра VINS на EKF
  (ray_tracer) → фантомная скорость IPM в ветре (VELXY=0). Три позиции превращаются в лесенку опор: вверх = наш
  стек (демпфер → VinsHold после хэндовера), центр = штатный LOITER (когда гейт
  открыт; до того — чистый ALT_HOLD с одним предупреждением в лог), вниз = MANUAL
  (всегда ALT_HOLD — seize отдаёт стики в предсказуемой семантике «наклон»).
  A/B «наш VinsHold против Loiter полётника» — одним щелчком в одном полёте.
  Выход из LOITER при протухании VINS — автоматический откат в ALT_HOLD
  (гистерезис 3×fresh, режим не дёргается на мигании свежести). Команда — та же
  P2s-freefly плюс:

  ```bash
  BS_FF_LOITER=1 BS_HANDOVER_VINS=1 BS_GZ_CMD_GAIN=4 \
  BS_VISION_VEL=1 BS_VISION_POSE_SRC=extern BS_GPS_DISABLE=1 \
  BS_MISSION="freefly" BS_PILOT=joy BS_STAB=DpHoldM ...
  ```

  В Loiter живость стиков задаёт САМ полётник (`LOIT_SPEED`/`PILOT_SPEED_UP`, не
  наши гейны) — ощущения «вверх» и «центр» будут разными, это и есть предмет
  сравнения. Дисциплина из GPS-denied серии действует: щёлкать в центр — в
  спокойном ховере, не на старте манёвра.

  **Тайминг для пилота.** EK3 уходит на extnav только на ЗРЕЛОМ VINS —
  `odom ≥ max(600, 2×BS_VINS_MIN)`, ≈25 с после схождения (полёт №3 2026-08-20:
  свап на 3-секундном VINS с враньём перемещения до ×10 подорвал EKF —
  «variance: position lost» — и до посадки позиция не вернулась; стики пилота
  были в центре, «спокойных стиков» недостаточно). Порядок в логе: `✅ VINS
  сошёлся` (хэндовер, тумблер вверх уже на VinsHold) → ~15-25 с спустя пары
  `EK3_SRC1_*: установлен` → `SIM_GPS1_ENABLE: установлен` (глушение GPS,
  ещё +6 с зрелости) — только ПОСЛЕ этого центр CH6 даст LOITER. Щёлкнул
  раньше — честный отказ «LOITER не готов»/«не латчит», вернись вверх и жди.

  ⚠️ **В extern-профиле EKF ест ТОЛЬКО позу VINS** (на зрелости ставится
  `EK3_SRC1_POSXY=6, VELXY=0`): скорость IPM в ветре фантомит (полёт №5
  2026-08-20: IPM слал 1.5-2.6 м/с при истинных 0.1-0.2 → варианс-ратио 1.72 в
  миг свапа → циклы EKF Failsafe/LAND). Если FCU сам ушёл в LAND по failsafe —
  freefly-центр его уважает (не ре-ассертит), тумблер вверх забирает борт.

  ⚠️ **Не армить сразу после запуска** (полёт 2026-08-20: арм на 17-й секунде
  после бута → EK3 не успел начать aiding, в воздухе уже не начал — const_pos
  весь полёт, «Loiter failed: requires position» при живых VISP/VISV). С
  `BS_FF_LOITER=1` план несёт `ekf_warmup`: газ прижат, руддер-арм невозможен,
  пока EKF не захватит позицию — ждать в логе `EKF держит позицию — к арму`
  и армить после. Вторая страховка там же: GPS не глушится, пока EKF не держит
  позицию (гейт по свежести local_position) — без aiding миссия остаётся на
  GPS. Если FCU всё же отказывает в LOITER >5 с при открытом гейте — в лог
  падает честное `LOITER: FCU не латчит режим… ФАКТИЧЕСКИ чистый ALT_HOLD`
  (борт дрейфует с ветром, центр = пустой стек) — щёлкай вверх.

⚠️ **Открытая ветка (боевой борт).** На Orin то же самое: пока нода оверрайдит ch1..4,
стики радио исчезают из телеметрии. Намерение на борт нужно доставлять мимо FCU
(отвод RC-линии на Orin / второй приёмник / форвардинг каналов OpenHD/ELRS) —
решить до боевого flow_assist. ⚠️ И FCU-уровень safety петлёй ЗАДЕТ: `FLTMODE_CH`
на ch5 мы не оверрайдим, но смена режима не сбрасывает override — ch1..4 всё равно
идут от ноды. **Разбор и план — §5.**

## 5. Переезд на боевой борт: RX штатно в FCU + отвод на Orin (план)

Вопрос, с которого начался разбор (2026-09-09): «в симе пульт идёт мимо FCU по USB,
а на борту приёмник воткнут в порт полётника штатно — большая ли это проблема?»
Ответ: **петля переезжает на борт один в один** (это устройство ArduPilot, а не
артефакт сима), но архитектурно это малая правка — один адаптер за портом
`PilotInput`. Рядом лежит настоящий блокер — **безопасности**, и он от переезда не
зависит: он есть уже сейчас, даже со скриптовым пилотом.

### 5.1 Что будет, если RX воткнуть штатно и ничего не менять

`RC_CHANNELS_OVERRIDE` поканально ЗАМЕЩАЕТ `radio_in`, телеметрия `RC_CHANNELS`
(→ `/mavros/rc/in`) отдаёт наши же значения, пред-override RC в MAVLink не
существует (§3). Значит: стики в FCU физически есть, но **нода их не видит** —
`rc/in` эхо её команды (`RosPilot`, `ros_pilot.py:200`, помечен ЛЕГАСИ). В assist
самораскачка, в MANUAL-seize защёлка. Параметром не лечится.

### 5.2 Блокер, который важнее петли

Докстринг `Arbiter` (`control_pkg/application/arbiter.py:14`) обещает: «на боевом
борту `FLTMODE_CH` — второй барьер, пилот сорвёт override на уровне FCU».
**Это неверно:** ArduPilot не сбрасывает override при смене режима — пилот щёлкнет
в STABILIZE, а ch1..4 продолжат приходить от ноды на 20 Гц. Аварийный выход сегодня
один: убить ноду и ждать `RC_OVERRIDE_TIME` (в дампе борта — 3 с).

Хуже, по дампу `distro/doc/Ardupilot_Params/MP/params.txt`: `FLTMODE1..6 = 2` —
**все шесть позиций ALT_HOLD**, т.е. щелчок тумблера сегодня и режим-то меняет
формально.

И третье, чего в старом разборе (`doc/tmp/tmp/cmd.txt`) нет: `JoyPilot` при потере
пульта **держит последние значения** (`ros_pilot.py:153`), сторожа свежести в коде
нет. А пока нода льёт override, FCU скорее всего не увидит и потерю радиолинка
(`FS_THR_ENABLE=1` не сработает — override держит `radio_in` живым). Потеря пульта =
борт летит с замороженными стиками и без failsafe. **Проверить матрицей на стенде**
(TX off / линк ноды off), но закладываться на «FCU спасёт» нельзя.

### 5.3 Лестница решений (от дешёвого к большому)

**Шаг 1 — seize через release (часы работы; НЕ СДЕЛАН).** У `RC_CHANNELS_OVERRIDE`
значение **0 = «отпустить канал обратно радио»** (у нас в ходу только
`RC_NOCHANGE = 65535`, `domain/rc.py:14`). MANUAL должен не транслировать стики, а
ПЕРЕСТАТЬ оверрайдить: `Arbiter` → актуатор шлёт 0 на ch1..4 → FCU мгновенно
возвращается к физическому приёмнику, нода выходит из цепочки. Туда же — сторож
свежести пульта (нет `/joy`/каналов N мс → тот же release). Это делает FCU-барьер
настоящим. В симе с `JoyPilot` passthrough остаётся как есть. Сейчас в коде этого
нет: `Arbiter.resolve` возвращает сырые стики, release-семантики в
`MavrosActuator` нет. Плюс минутная проверка в SITL, что наш Copter трактует 0 по спеке.

**Шаг 2 — отвод RC на Orin (боевой путь).** Приёмник на борту — **CRSF/ELRS**:
`SERIAL1_PROTOCOL=23 (RCIN)`, `SERIAL1_BAUD=421` (420000). Это не инвертированный
UART 3.3 В — идеальный кандидат для пассивного отвода (SBUS потребовал бы инвертор).

**Шаг 3 — уйти от override как канала актуации** (GUIDED/attitude-target): `rc/in`
снова честный, FCU-seize по построению, отвод не нужен. Но это смена домена выхода
и перетюнинг всей кампании — гейны, тримы, станция, WindTrim считаны в PWM. Не сейчас.

### 5.4 Шаг 2 подробно: отвод, а не «переткнуть»

⚠️ **Переткнуть RX из FCU в Orin — нельзя.** FCU остаётся без радио: нет
`FLTMODE_CH`-барьера, нет руддер-арма, нет RC-failsafe, а шаг 1 теряет смысл —
отпускать каналы становится некому. Смерть Orin = потеря борта. Весь смысл
безопасности в том, что у FCU есть СВОЁ радио.

**Правильно — Y-отвод той же линии:** сигнал гонит приёмник, FCU и Orin оба сидят
на нём ВХОДАМИ. Два провода: сигнальная линия «TX приёмника → RX полётника»
параллельно на RX Orin, и общая земля.

- ⚠️ **TX Orin к этой линии не подключать никогда.** Обратный провод (FCU →
  приёмник) — телеметрия; два драйвера = contention. Если у приёмника half-duplex
  (одна линия на всё), Orin увидит ещё и кадры телеметрии FCU — фильтровать по типу
  кадра и CRC, но пин держать строго входом.
- Jetson 40-pin — 3.3 В и **не 5-В-толерантен**. ELRS обычно 3.3 В, но замерить
  перед подключением; последовательный резистор ~1 кОм как страховка.
- Питание приёмника не трогаем — как сейчас, от FCU.
- Какой пад несёт каналы — проверить логическим анализатором/осциллом, не по цвету
  провода.

**Куда втыкать на Orin:**

- **USB-TTL свисток** (FT232 / CP2102) → `/dev/ttyUSB0` — самый безопасный вариант:
  не трогаем pinmux, не рискуем консолью, механически надёжнее dupont'ов на хедере.
  CH340 не брать (табличные боды).
- **Header UART (пины 8/10) свободен**: связь с полётником идёт по USB
  (`/dev/ttyACM0`, 2 Мбод — `distro/etc/mavlink-router/main.conf`). Проверить
  `ls /dev/ttyTHS*`, снять с порта getty (`nvgetty`), не путать с `ttyTHS0` из
  старого конфига (`distro/doc/log.txt:87`) и с отладочной консолью (JetPack 6 —
  обычно `ttyTCU0`).
- ⚠️ **420000 — нестандартный бод**: нужен `termios2`/`BOTHER`. pyserial на Linux
  умеет, FTDI/CP2102 тоже — но поймать кадры живьём ДО сборки борта.
- Если у приёмника есть **второй выход** (многие ELRS-RX умеют второй протокол на
  отдельном паде) — это чище Y-тапа: отдельная линия на Orin. Второй CRSF —
  идеально; SBUS на втором паде потребует инвертор.

**Софт — почти нечего делать.** Мостик CRSF→`/joy`: парсер кадра `0x16`
(RC_CHANNELS_PACKED, 16 каналов по 11 бит, CRC8 DVB-S2) → `sensor_msgs/Joy` с теми
же индексами, что даёт EdgeTX-HID. Дальше `JoyPilot` и весь стек ниже — **без
единой правки**, контракт топика тот же, что в симе. Перевыверить на земле:

- масштаб CRSF 172..1811 → PWM 988..2012 → наша конвенция `(PWM−1500)/400`;
- **знаки станут ПРЯМЫМИ** — зеркало roll/yaw/throttle было артефактом USB-HID;
  перемерить `joy_check.sh`, поправить `BS_JOY_SIGNS`;
- SA/SD приедут **осями**, не `buttons[]` — код готов: `parse_land_src` понимает
  `a<i>` (`ros_pilot.py:102`), т.е. `BS_LAND_JOY=a9` и т.п.;
- квирк «CH8 дерётся с CH7 за `axes[6]`» исчезает — он тоже HID-овский, CH8
  освобождается.

**Контейнер:** в `docker/orin/docker-compose.yml` стоит `privileged: true`, но
по-хорошему добавить `devices: - /dev/ttyUSB0:/dev/ttyUSB0` явно (после правки
compose — пересоздание контейнера).

**Чего отвод НЕ отменяет:**

- шаг 1 всё равно нужен: отвод даёт ноде честные стики, но не даёт пилоту отобрать
  каналы — пока нода пишет override, физическое радио в контур не вернётся;
- один приёмник = **общая точка отказа** FCU и Orin. Второй ELRS-RX её разносит
  (несколько приёмников на один передатчик — штатно), ценой ~15 $, веса и своего
  линк-бюджета. Отвод дешевле; выбор зафиксировать сознательно.

### 5.5 Грабли карты каналов (проверить до первого полёта)

- ⚠️ **`RC7_OPTION=31` на борту = Motor Emergency Stop**, а в симе CH7 — SF-мастер
  сырых стиков (`rx.md`). Щелчок SF на борту = стоп моторов. **Перемапить
  обязательно.**
- `FLTMODE_CH=5` при всех позициях ALT_HOLD — сделать хотя бы одну позицию честным
  выходом (STABILIZE/LAND) в пару к шагу 1.
- `RC_OVERRIDE_TIME=3` — осознанно уменьшить (наш override идёт 20 Гц, 0.5–1 с с
  запасом), иначе после смерти ноды борт 3 с летит замороженной командой.
- `ARMING_RUDDER=2` работает при любой схеме, но арм надёжнее сервисом.

⚠️ Все параметры выше — из `distro/`, а это ЗАМОРОЖЕННЫЙ снимок старого состояния
Jetson. Перед деплоем сверить на живом борту (`ros2 param list /mavros/param`), тем
более что в 4.8 часть имён переехала (память `ardupilot-48-param-renames`).

### 5.6 Порядок работ

1. Шаг 1 (release-seize + сторож свежести пульта) — оффлайн-тест + проверка
   семантики нуля в SITL по дисциплине прогона. Заодно поправить враньё в докстринге
   `Arbiter`.
2. Матрица failsafe при активном override в SITL: TX off, линк ноды off, нода
   убита — что делает FCU.
3. Наземный стенд отвода: приёмник + FCU + Orin на столе, мостик CRSF→`/joy`,
   `joy_check.sh` — стики глазами ноды, сверка знаков и индексов.
4. Перемапить CH7 (motor estop!) и FLTMODE, сверить параметры на живом борту.
5. Только после этого — первый полёт с нодой в контуре.
