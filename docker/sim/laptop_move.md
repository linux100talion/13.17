# Переезд на ноутбук с RTX 4060 — чек-лист и что там меняется

Стенд до сих пор жил на GCE-боксе **без GPU** (ветка CPU-оверрайда, `CPU=1`,
llvmpipe, RTF ≈ 0.07). Цель переезда — реальное время в Gazebo и **живой пульт**
вместо скриптованного пилота. Здесь то, что понадобится в первый час на новой
машине, и то, что от смены RTF ломается не сразу и молча.

---

## 1. Поднять стенд (по порядку)

```bash
# хост: драйвер NVIDIA + docker + nvidia-container-toolkit (проверка)
nvidia-smi
docker run --rm --gpus all nvidia/cuda:12.2.2-base-ubuntu22.04 nvidia-smi

git clone -b nn2_c3_control2 https://github.com/linux100talion/13.17 /root/13.17
git clone --branch 1317_debug https://github.com/linux100talion/VINS-MONO-ROS2 \
          /root/VINS-MONO-ROS2          # ⚠️ форк живёт ВНЕ репы, монтируется bind-mount'ом

cd /root/13.17/docker/sim
make host-setup     # xhost + v4l2loopback (/dev/rawbayer), нужен sudo
make build          # долго: SITL + Gazebo + OpenCV с CUDA из исходников
#   RTX 4060 (Ada) = CUDA_ARCH_BIN 8.9. Дефолт в nav/Dockerfile ("7.5;8.0;8.6;8.9")
#   её уже включает, так что соберётся и без правок — но сборку сильно ускорит
#   --build-arg CUDA_ARCH_BIN=8.9 (одна арка вместо четырёх).
make up && make wait
make sitl-cal       # ОДНОРАЗОВО после первого подъёма/после make clean
```

**`CPU=1` больше не нужен** — это флаг GPU-less бокса. Со всеми таргетами идём без него.

Первый прогон-проверка (он же образец дисциплины: атомарно, целиком):

```bash
NAME=L0 bash /root/13.17/src/lab/calib_run.sh
```

## 2. Что меняется от RTF 0.07 → ~1 (грабли, каждая уже кусалась)

**Камеру можно вернуть на 1280×720.** CPU-оверрайд занижал её до 320×180
(`CAMERA_W/H` в `docker-compose.cpu.yml`), llvmpipe больше не тянул; вся кампания
`YW/IG/BW` летала на 960×540 (`RES=960x540` — это и есть `CAMERA_W/H`, дефолт
`calib_run.sh`). Под 1280×720 посчитаны интринсики `sim.yaml`
(`fx=fy=640, cx=640, cy=360`), так что на GPU-боксе VINS впервые поедет на своём
расчётном разрешении — но менять разрешение и сравнивать с кампанией одновременно
нельзя. Порядок: сначала переснять базу (3 прогона конфигом `YW3s`) на том
разрешении, на котором дальше летим, и только потом мерить новое против неё.

**Частота кадров вырастет — а окна и гейны считались в КАДРАХ.** `yaw_smooth` — окно
медианы в кадрах, `arm_frames` — кадры, `ipm_win` — секунды (это ок). Сглаживание курса
уже ловили на этом: оно ведёт себя как ВРЕМЕННОЕ окно, а не как «5 кадров», и при смене
fps эквивалент меняется. Проверить `yaw_smooth` и всё, что считает кадры, первой же
серией.

**Бюджеты в sim-секундах переносятся без правок** (`SIM_BUDGET`, `*_BUDGET`), а вот
wall-таймауты — нет: `ARM_WALL_CAP` (дефолт 1200 с в `arm.sh`) ставился с запасом под
RTF 0.07 и на новой машине просто избыточен, но `make wait` (5 мин) и таймаут ожидания `/dev/rawbayer` (60 с) рассчитаны
на медленный бокс — если что-то падает по таймауту, смотреть туда.

**Диск и видео.** При RTF ≈ 1 сырой bag с `/image_color` растёт в разы за то же
sim-время. `hover_series.sh` потрошит бэги сразу после прогона (`STRIP=1`) — не
отключать. `make logs` и `df -h` держать под рукой.

**IMU-патчи VINS остаются нужны** (`timesync_mode:=NONE` + skip-патч в
`estimator_node.cpp`, ветка `1317_debug`): причина в SITL-протоколе, а не в скорости
машины. Но `/clock` ~155 Гц против 250 Гц IMU на быстрой машине даст другую картину
дубликатов — если в логе VINS снова появится `imu message in disorder`, начинать
разбор оттуда.

## 3. Живой пульт: что уже готово и что предстоит

**В коде пилот-путь есть целиком, менять домен не надо:**

| слой | файл | роль |
|---|---|---|
| источник | `control_pkg/infrastructure/ros_pilot.py` → `RosPilot` | читает `/mavros/rc/in`; тумблер режима — **канал 6, порог 1700** |
| замена на время сима | тот же файл → `ScriptedPilot` | детерминированный профиль стиков по sim-времени |
| намерение | `domain/control/trajectory.py` → `RcTransmitter` | стик → цель скорости (нормировка `pilot_deadzone=30`, `pilot_full=400`, знаки `pilot_*_sign`) |
| выход | `infrastructure/mavros_actuator.py` | `/mavros/rc/override`, каналы 1..4 |

То есть «переключить на реальный пульт» = подменить `ScriptedPilot` на `RosPilot`
и довести физические стики до `/mavros/rc/in`. Боевой сценарий пре-VINS уже собран:
`control_mode=flow_assist` (демпфер крена+курса, тангаж — сырой стик) либо
`BS_STAB=DpRollHold+DpYawHold` с миссией-плейлистом.

**Что предстоит сделать на новой машине:**

1. Довести пульт до SITL. Порядок предпочтения: (а) TX в режиме USB-джойстика →
   MAVProxy `module load joystick` на том же tcp:5760, что уже раздаёт
   `mavlink_router`; (б) свой мостик joy→`RC_CHANNELS_OVERRIDE`. Вариант с прямым RC-in
   портом SITL (UDP, обычно 5501) — **проверить, а не считать данностью**.
2. Убедиться, что стики реально видны: `ros2 topic echo /mavros/rc/in` — каналы 1..4
   ходят за стиками, канал 6 щёлкает тумблером.

⚠️ **ГЛАВНАЯ ЗАСАДА, проверить ПЕРВОЙ.** Наша нода непрерывно пишет
`/mavros/rc/override`, а `RosPilot` читает `/mavros/rc/in`. Если ArduPilot отдаёт в
`RC_CHANNELS` уже ПОДМЕНЁННЫЕ override'ом значения, пилот прочитает собственную команду
как «стик пилота» — замкнутая петля, которая выглядит как «борт сам себя разгоняет», а
не как ошибка проводки. Проверяется за минуту, до всякого полёта: поднять стек, руками
покрутить стик, посмотреть `rc/in` при активном override и при выключенном. Если петля
есть — источник намерения брать не из `rc/in`, а из отдельного топика (joy) мимо FCU.

⚠️ Второе: `pilot_pitch_sign = -1.0` парный к `_PITCH_RC_SIGN` в `ControlStack` — вместе
они дают pass-through. С реальным радио знаки сверить ЗАНОВО, на земле, по одному стику
за раз. Зеркальный знак уже стоил разбора один раз (`6841c58` — тест впрыска команды
держал зеркальный знак стика).

## 4. Где сейчас управление (чтобы не начинать с нуля)

- **Настройка демпфера и вся история кампаний** — `src/control/tune.md`. Последний
  раздел: гейты вида сверху проверены на 12 прогонах и **отвергнуты** (`ipm_max_speed`,
  `ipm_alt_band_*`, `ipm_arm_frames` = 0), механизм оставлен в коде.
- **Открытая ветка №1** — вычитать фантом набора из канала вида сверху, а не глушить
  канал: фантом измерен и линеен по вертикальной скорости (+0.67 м/с на м/с продольно,
  +0.25 вбок).
- **Открытое, не закрытое кампанией:** срыв `conf=0.00` на старте (1 прогон из 6 молча
  отключает все три оси); входной переходный процесс как остаток бюджета ошибки;
  конверт (порывы, ветер > 5 м/с, косой ветер) не проверен.
- **Разбор бэгов:** `src/lab/flight_cmp.py` (вход/висение/посадка + рули),
  `src/lab/flight_timeline.py` (покадровая лента одного прогона),
  `src/lab/gate_replay.py` (прокрутить доменный класс по кадрам из бэга — так ловятся
  расхождения «что решала стратегия» против «что попало в бэг»).
- **Конфиги всех прогонов кампании** — `src/control/swips/*.env` (включая `YW3s`,
  `IG1s`, `IG2s`, `BW0s`, `BW1s`).

Дисциплина прогона не меняется от машины: стек поднимать целиком, прогон атомарен от
рестарта до записи bag, `src/control`/`src/mission` **не править на живой серии** —
каждый прогон пересобирает colcon из bind-mount'а.
