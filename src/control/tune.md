# src/control — КАК НАСТРАИВАТЬ ДЕМПФЕР ЗАНОВО (план прогонов по трём осям)

Если бы настройку `Dp*` пришлось начинать с чистого листа — вот порядок прогонов, который
я бы выполнил, и почему именно такой. Порядок выведен из ошибок этой кампании: почти всё
потерянное время ушло на настройку контура против неизмеренного датчика и на выводы по
одиночным прогонам.

Ручки и их текущие значения — `ToDo2.md`. Механизм звона тангажа — `ToDo3.md`. Впрыск
команд — `control.md`. Здесь только МЕТОДИКА.

## Семь правил, из которых растёт весь план

1. **Датчик раньше контура.** Настраивать петлю, не зная corr/крутизну/задержку её
   сигнала, — это подгонка под шум. Цена нарушения в этой кампании: серия `K2s` (kd 5000
   → 9000) сделала хуже, потому что D-член был наполовину шумом; `L1_mvfwd` показал, что
   гейн канала положения гуляет 0.35 / 1.81 / 1.46 внутри ОДНОГО полёта.
2. **Одна ось за раз, остальные держит оракул.** `GzRollHold`/`GzPitchHold`/`GzYawHold`
   держат по истинной позе Gazebo. Ось под настройкой — единственная, где работает `Dp*`;
   иначе увод одной оси уезжает в сигнал другой (крен создаёт боковой поток, который
   тангаж читает как масштаб).
3. **Ничего не значит одиночный прогон.** Разброс стенда снят шестью одинаковыми
   прогонами: **11.6 ± 0.9 м** (8%). При одном и том же конфиге встречались 7.7 и 13.1 м.
   Любое «стало лучше» — это серия из трёх (`hover_series.sh`) и t-критерий.
4. **Одна ручка на серию.** Две ручки сразу — и результат не атрибутируется. Исключение:
   ручки, связанные физикой (kp и kd меняются парой при заданном ζ), но тогда пара
   считается одним изменением и обосновывается формулой ДО прогона.
5. **Прогон атомарен.** Перезапуск всего стека → `make wait` → полёт → бэг. Ручной
   рестарт отдельного процесса даёт ложные диагнозы. Скрипты `src/lab/*.sh` НЕ править,
   пока прогон идёт (bash дочитывает файл на ходу — миссия ушла на второй круг).
6. **Порог ищут по НАСЫЩЕНИЮ, а не по дрожи.** Интуиция «слишком большой гейн → мелкая
   дрожь» на этих осях НЕ работает. Замер R6 (`roll_kp` 96 и 160): частота смен знака
   выхода 0.3–0.4 /с — НИЖЕ, чем на рабочих 32–48, то есть по «дрожи» порога нет вовсе.
   А выход при этом стоял в клампе 150 на 40–50% времени, и борт болтало 0.72 м/с против
   0.21 у базы. Большой размах PWM при РЕДКОЙ смене знака = медленные качели
   недодемпфированной петли в насыщении. То же у тангажа при `kd=5000` (Д-пик ровно 150
   половину висения). **Смотреть долю потолка; PWM СКО в одиночку метрикой не является** —
   она растёт линейно с гейном по построению (27→36→57→107 на kp 16→32→48→96).
7. **Команду проверять по СЕМАНТИКЕ, а не по факту «доехала».** Приёмка «стик даёт
   заданную скорость» проходит и у оси, которая не умеет останавливаться. Для `rate`-оси
   семантика — «отпустил → скорость в ноль», и её надо мерить отдельным числом (выбег
   после снятия команды). В кампании R выбег 1.5–4.3 м нашёлся ТОЛЬКО потому, что
   проверялась семантика; по приёмке команды ось проходила.

## Как запускать: прогоны и разбор

**Серия/свип — heredoc'ом целиком, НЕ `sed`'ом по предыдущему скрипту.** Замена `N=1` на
`N=3` однажды попала в `BS_ROLL_OSIGN=1` и в хвост `BS_ROLL_CMD_GAIN=10` — серия ушла в
воздух с перевёрнутым знаком оси и тройным гейном. Не падает, а даёт правдоподобно
странный полёт.

```bash
cat > /tmp/rN_run.sh <<'EOF'
#!/bin/bash
for pair in "R8a:0" "R8b:1.5"; do          # свип: одиночки, PREFIX:значение
    pre="${pair%%:*}"; val="${pair##*:}"
    env N=1 PREFIX="$pre" \
        BS_STAB=GzPitchHold+GzYawHold+DpRollHold \
        BS_MISSION=climb3,hover5,mv_right6,hover8,mv_left6,hover8,land \
        BS_SLEW=300 BS_FENCE=25 BS_FLOW_OBS=1 BS_THROTTLE_CLIMB=1800 \
        BS_MODE_BUDGET=80 BS_ARM_BUDGET=80 BS_CLIMB_BUDGET=120 BS_LAND_BUDGET=180 \
        BS_ROLL_KP=48 BS_ROLL_KI="$val" BS_ROLL_IMAX=150 BS_ROLL_OSIGN=1 \
        BS_ROLL_SMOOTH=25 BS_ROLL_CMD_GAIN=10 \
        GDRIVE_UP=1 MP4=1 \
        bash /root/13.17/src/lab/hover_series.sh
done
echo "######## СВИП ЗАВЕРШЁН ########"
EOF
grep -E "N=|KP=|KI=|OSIGN|CMD_GAIN" /tmp/rN_run.sh    # ГЛАЗАМИ сверить ДО запуска
setsid nohup bash /tmp/rN_run.sh > docker/sim/output/RN.log 2>&1 < /dev/null & disown
```
Серия n=3 — тот же скрипт без цикла, с `N=3 PREFIX=R9s`. `GDRIVE_UP=1 MP4=1` —
обязательно (видео на Drive). Отсоединённый запуск (`setsid nohup … & disown`) переживает
обрыв ssh; ждать — `until grep -q "ЗАВЕРШЁН" …; do sleep 60; done`.

**Разбор — из образа, без поднятого стека.** Контейнер `p1317_nav` между прогонами лежит,
а перезапускать его ради чтения бэга нельзя (дисциплина прогона). Одноразовый контейнер
с бэгами и скриптами только на чтение:

```bash
D="docker run --rm --network none \
   -v /root/13.17/docker/sim/output:/out:ro -v /root/13.17/src/lab:/lab:ro \
   sim-nav:latest bash -lc"
$D "source /opt/ros/humble/setup.bash; python3 /lab/<скрипт> <аргументы>"
```

| Что мерим | Скрипт | Аргументы |
|---|---|---|
| уход/размах/период/потолок/H СКО | `hover_stats.py` | `/out/N1s1_bag /out/N1s2_bag …` |
| разложение выхода на П и Д | `pd_split.py` | `KD=1500 … /out/N1s1_bag` (env `KD`) |
| здоровье опоры (kf_n, сегменты, пересевы) | `kf_health.py` | `/out/N1s1_bag …` |
| паспорт бокового датчика | `roll_sensor_check.py` | env `BAG=/out/…` ⚠️ бэг новее `be8688f` |
| калибровка боковой команды | `roll_cmd_check.py` | env `BAG=`, `GAIN=`, `S_LAT=` |
| выбег после снятия команды | `roll_brake_check.py` | `R7s1:48 R4s1:16 …` (бэг:значение) |
| потолок/период/размах на висении | `roll_osc_check.py` | то же |
| чистый снос (метрика для `ki`) | `roll_drift_check.py` | то же |
| сегменты курса, калибровка `S` | `yaw_seg_check.py` | env `BAG=`, `S=` |

⚠️ Пути монтирования — АБСОЛЮТНЫЕ. `-v "$PWD/output:/out:ro"` молча подставит не тот
каталог, если оболочка не в `docker/sim`, и бэг «не найдётся» при живом файле.

## Фаза 0 — паспорт стенда (2 прогона)

Прежде чем что-то улучшать, надо знать, что такое «не изменилось».

```bash
N=2 PREFIX=B0s BS_STAB=none BS_MISSION="climb3,hover40,land" bash src/lab/hover_series.sh
```

Без стабилизаторов, открытый контур. Снимаем: свободный уход за 40 с, его разброс, RTF,
темп кадров перцепта, темп IMU. Это нулевая линия и одновременно проверка, что стенд
здоров (не «Main loop slow», не просевший fps).

## Фаза 1 — паспорт ПРОВОДА (3 прогона, по одному на ось)

Что команда делает с бортом, БЕЗ обратной связи. `BS_STAB=none`, движение задаётся
профилем миссии:

| ось | миссия | что достаём |
|---|---|---|
| крен | `climb3,mv_right6,hover4,land` | °/PWM, τ, знак провода |
| тангаж | `climb3,mv_fwd6,hover4,land` | то же, продольно |
| рыскание | `climb3,mv_cw6,hover4,land` | °/с на PWM |

Эталонные значения этой кампании: **k = 0.0735 °/PWM**, **τ = 0.27 ± 0.03 с**,
**a₁ = 0.0115 м/с²/PWM**, полный стик 400 PWM. Знак провода у осей РАЗНЫЙ и это не
опечатка: у крена PWM>1500 = разгон вправо, у тангажа PWM>1500 = нос вверх = разгон
НАЗАД. Отсюда `roll_osign=+1`, `pitch_osign=+1` при однознаковых сигналах.

Здесь n=1 достаточно: эффект на порядок больше разброса. На знаке — не экономить, это
единственная ошибка, которая переводит демпфер в РАЗГОН (замер `H4_mask`: борт
разогнало до 12.8 м/с и положило раму на −12.9°).

## Фаза 2 — паспорт ДАТЧИКА (0 новых прогонов, офлайн по бэгам фазы 1)

Самая дешёвая и самая доходная фаза: считается по уже снятым бэгам, полётов не нужно.
Инструмент — `src/lab/kf_vel_check.py` (переигрывает боевой `FlowEstimator` по кадрам
бэга) и `src/lab/mvfwd_check.py`.

По каждой оси считаем против истины (одометрия Gazebo):

| величина | зачем | порог годности |
|---|---|---|
| corr сигнала с истиной | видит ли ось вообще | > 0.8 |
| крутизна (ед./м или ед./(м/с)) | масштаб для пересчёта гейнов | стабильна ±20% по сегментам |
| остаток производной | можно ли вообще ставить kd | < 30% рабочей скорости |
| задержка контура | потолок полосы | измерить, а не предполагать |

**Это ворота.** Ось, не прошедшая пороги, в фазу настройки НЕ идёт — сначала чинится
канал. Пример из кампании: продольная скорость в межкадровом сдвиге имеет corr −0.22
(канал слеп) — поэтому тангаж переведён на `kf_logs` (масштаб), а не докручен гейнами.
Второй пример: ω из `gz_imu` с low-pass 5 Гц роняла corr положения 0.89 → 0.61; переход
на MAVROS ATTITUDE поднял её обратно — это была правка ПЕРЦЕПТА, а не контура.

## Фаза 3 — РЫСКАНИЕ первым (5–7 прогонов)

Почему первым: петля первого порядка (самая простая), а её ошибка загрязняет обе
поступательные оси — перцепт вычитает вращательный поток по ω, и остаточное рыскание
уезжает прямо в оценку смещения.

```bash
BS_STAB="GzRollHold+GzPitchHold+DpYawHold" BS_MISSION="climb3,hover40,land" \
  BS_YAW_KP=<свип> BS_YAW_KI=0
```

Свип `kp` одиночными прогонами (4, 6, 10, 16) — ищем порог дрожи; берём вдвое ниже
порога. Затем **проверка победителя серией n=3** против базы. `ki` пробуем ТОЛЬКО если
виден устойчивый снос курса; в этой кампании интеграл оказался вреден (смещение
`yaw_flow` копится) — победил `kp=6, ki=0, сглаживание 5`.

Отдельно: сглаживание — это ВРЕМЕННОЕ окно, а не число кадров. При смене fps его надо
пересчитывать, иначе настройка «переезжает» вместе с нагрузкой стенда.

```bash
$D "source /opt/ros/humble/setup.bash; BAG=/out/Y5s1_bag S=0.324 python3 /lab/yaw_seg_check.py"
```

## Фаза 4 — КРЕН (6–8 прогонов; фактически ушло 9 — кампания R)

Петля по СКОРОСТИ (сигнал `flow_lateral` — межкадровый сдвиг), первого порядка. Звенеть
не может, поэтому настраивается быстро. ⚠️ «Не может звенеть» ОТНОСИТСЯ К ПЕТЛЕ, а не к
контуру целиком: при большом `kp` выход упирается в кламп, и связка «насыщенный выход +
инерция борта» качается как угодно (замер R6 ниже).

Миссия для крена — НЕ `hover40`, а с командными проездами: половина дефектов оси видна
только под командой.

```bash
BS_STAB="GzPitchHold+GzYawHold+DpRollHold" \
BS_MISSION="climb3,hover5,mv_right6,hover8,mv_left6,hover8,land" \
  BS_ROLL_KP=<свип> BS_ROLL_KI=3 BS_ROLL_IMAX=150 BS_ROLL_CMD_GAIN=10
```

1. **Сначала КОМАНДА, потом гейны.** Проверить знак и калибровать `cmd_gain` по
   `roll_cmd_check.py` (заказ `c_right·gain/S_lat` против истинной скорости). Замер R2/R3:
   знак был ЗЕРКАЛЕН (`mv_right` уводил влево на 4.38 м), а сам гейн 10 оказался верен
   (10.7 ± 0.9). Настраивать гейны на зеркальной команде бессмысленно: промежуточный
   разбор R2 дал «77% отдачи и смещение −0.23 м/с», и это целиком артефакт зеркала.
2. `kp` свипом одиночных (16, 32, 48, 96, 160) → порог → вдвое ниже. **Порог тут — доля
   ПОТОЛКА, а не дрожь** (см. правило 6).
3. `ki` — здесь он ОСМЫСЛЕН (петля по скорости позицию не держит, интеграл её
   подтягивает), свип (0, 1.5, 3) при `imax` 150. ⚠️ В кампании R так и НЕ проверен:
   `ki=3` стоит по наследству от монолита.
4. Победитель — серией n=3 против базы, и мерить ОБЕ стороны размена (см. приёмку).

**Приёмка — две метрики, а не одна.** Одной мало: удержание и торможение тянут `kp` в
разные стороны, и по любой одной ось «принимается» с невыявленным дефектом.

- *удержание*: доля потолка, средняя `|v|` и РАЗМАХ `v` на свободном висении
  (`roll_osc_check.py`). Эталон на `kp=48`: 5% потолка, |v| 0.29 м/с, размах 3.1–3.9 м/с;
- *торможение*: выбег вбок за 6 с ПОСЛЕ снятия команды (`roll_brake_check.py`). Эталон:
  **1.13 ± 0.43 м** вправо, **0.81 ± 0.35 м** влево;
- *снос* (только для свипа `ki`): `roll_drift_check.py` — чистое смещение по свободным
  участкам и отношение `|снос|/|путь|`. База на `ki=3`: −1.61 ± 1.55 м, направленность
  0.09–0.44. ⚠️ Разброс почти равен эффекту — одиночка значима, только если вылетит
  далеко за полосу.

```bash
$D "source /opt/ros/humble/setup.bash;
    python3 /lab/roll_cmd_check.py                        # знак и gain, env BAG=
    python3 /lab/roll_brake_check.py  R7s1:48 R4s1:16     # выбег
    python3 /lab/roll_osc_check.py    R7s1:48 R4s1:16     # потолок/период
    python3 /lab/roll_drift_check.py  R8a1:0  R7s1:3"     # снос (для ki)
```

Итог кампании R: `kp` 16 → **48** (выбег 3.05 → 1.13 м ценой |v| 0.23 → 0.29 при
неизменном размахе), `cmd_gain=10` подтверждён, `ki` не проверен.

## Фаза 5 — ТАНГАЖ последним (8–12 прогонов, и только после ворот фазы 2)

Петля по ПОЛОЖЕНИЮ (`kf_logs` — логарифм масштаба), второго порядка: обязана звенеть без
честного демпфера. Самая дорогая ось, поэтому идёт последней.

```bash
BS_STAB="GzRollHold+GzYawHold+DpPitchHold" BS_MISSION="climb3,hover40,land" \
  BS_PITCH_KP=<из ω_n> BS_PITCH_KD=<из ζ> BS_PITCH_KI=0
```

Гейны берутся НЕ свипом, а расчётом от паспорта, и свипом только проверяются:

```
kp → ω_n = √(kp · крутизна · a₁)      целимся в ω_n втрое ниже 1/задержка_контура
kd → 2ζω_n                            ζ ≈ 0.9, но не выше, чем позволяет остаток D-канала
ki = 0                                интеграл по положению копит то, что и так копит kp
```

Обязательная проверка ДО прогона: `kd · (рабочая скорость)` должно быть заметно меньше
потолка `max_pwm=150`, иначе демпфер уйдёт в насыщение на собственном шуме. Именно это
убило `K2s` (kd=9000): 15.4 ± 4.0 м против базовых 11.6 ± 0.9 (t=2.33 при пороге 2.31).

**Итог кампании N (`pitch_kd`): расчёт указал не туда, решила доля потолка.** Расчётное
почти критическое ζ≈0.98 давало `kd=5000` — и на нём Д-пик у ВСЕХ прогонов ровно 150,
то есть половину висения выход стоял в клампе и П-член не значил ничего. `kd=1500`:
доля потолка 42–54% → 24–35%, вклад `kf_vel` в выход 111 → 57 СКО при НЕизменном
`|kf_vel|` (0.030) — то есть упал не сигнал, а гейн шума.

Ниже 1500 нельзя, и причина не в средней ошибке, а в РЕЖИМЕ. Прогон либо держится с
размахом 11–22 м, либо срывается в 28–38 м; промежуточных нет, и доля срывов растёт по
мере снижения `kd`:

| `kd` | 5000 | 1500 | 700 | ≤300 |
|---|---|---|---|---|
| срывов | 1 из 6 | **0 из 3** | 3 из 7 | 2 из 2 |

Одиночка на `kd=700` дала лучший прогон кампании (уход 10.7 м) — и серия n=3 на том же
значении дала 9.8 / 20.2 / 34.9. Гейн не меняет амплитуду плавно, он двигает контур к
границе устойчивости, а по какую сторону ляжет конкретный полёт, решает начальное
возмущение. **Мерить долю СРЫВОВ, а не среднее по серии.**

⚠️ Ложный след, чтобы не идти повторно: СКО высоты почти монотонно совпадало с
горизонтальным уходом, и напрашивалась цепочка «ушла высота → опора пересевается →
сегмент выбрасывается → П слепнет → уход». Опыт N4s (`kf_alt_max` 0.06 → 0.25, всё
прочее то же) обнулил выбросы (11/12/36 → 0/0/1) — и срыв всё равно случился при НУЛЕ
выбросов. Высота оказалась симптомом (срыв → крен → просадка тяги), а не причиной.

Разбор кампании тангажа:

```bash
$D "source /opt/ros/humble/setup.bash;
    python3 /lab/hover_stats.py /out/N1s{1,2,3}_bag       # уход/размах/потолок/H СКО
    KD=1500 python3 /lab/pd_split.py /out/N1s1_bag        # выход на П и Д
    python3 /lab/kf_health.py /out/N1s{1,2,3}_bag"        # здоровье опоры
```

Диагностика звона по бэгу: период автоколебания. Если при СНИЖЕНИИ `kp` период
УКОРАЧИВАЕТСЯ (замер `K4s1`: 6.3 с против базовых 7.4–8.6) — это не второй порядок, а
лимит-цикл по задержке/насыщению, и лечится он не гейнами, а снятием насыщения
(`slew`, потолок) или укорочением задержки.

## Фаза 6 — общие ручки (4–6 прогонов)

Это НЕ per-axis PID, их настраивают после осей, серией каждую:

- **`slew`** (PWM/с, ограничение скорости изменения выхода). Мало — борт отрабатывает
  огибающую вместо значений; много — доезжает чаттер. Признак «мало»: доля кадров в
  потолке ±150 (в `L1_mvfwd` было 46%). Текущая проверка: серия `M1s` на 800 против 300.
- **окна сглаживания** (`roll_smooth`, `pitch_smooth`, `yaw_smooth`) — пересчитывать при
  смене fps, см. фазу 3.
- **`cmd_gain`** — впрыск команд. У осей-скоростей это цель скорости, у оси-положения —
  скорость уставки (`control.md`). Проверяется миссией
  `climb3,hover10,mv_fwd5,hover20,land` по трём каналам разом: `/flow_dbg5` (уставка),
  `/flow_dbg3` (зрение), одометрия (истина).

## Фаза 7 — возмущение (6 прогонов)

Настройка, проверенная только на тихом стенде, ничего не стоит.

```bash
WIND_SPD=3 WIND_DIR_DEG=<боком к носу> …   # серия n=3
WIND_SPD=5 …                               # серия n=3
```

Ветер в Gazebo откалиброван замером (не по формуле плагина — она ошиблась впятеро):
**F ≈ 1.46 · factor² · v** Н, то есть отклик КВАДРАТИЧЕН по `WIND_FACTOR` и ЛИНЕЕН по
скорости ветра. Воспроизводимость силы 2–4%. Эталон: ветер 3 и 5 м/с стоят статистически
незначимых +1.8 / +1.4 м к уходу.

## Бюджет

| фаза | прогонов | зачем |
|---|---|---|
| 0 стенд | 2 | что такое «не изменилось» |
| 1 провод | 3 | °/PWM, τ, ЗНАКИ |
| 2 датчик | 0 (офлайн) | ворота: годна ли ось к настройке |
| 3 рыскание | 5–7 | чистит ω для обеих поступательных |
| 4 крен | 6–8 | петля по скорости |
| 5 тангаж | 8–12 | петля по положению |
| 6 общие ручки | 4–6 | slew, окна, cmd_gain |
| 7 возмущение | 6 | подтверждение под ветром |
| **итого** | **34–44** | ≈ 12–15 часов стенного времени |

Каждый прогон — 15–20 минут на CPU-боксе; серия из трёх — около часа. Бэги потрошатся
после каждого прогона (`STRIP=1`), иначе три по 2.6 ГБ не влезут; видео уходит на Drive
под именем прогона.

## Чего НЕ делать (всё это уже стоило времени)

- **Не выводить из одного прогона.** «J4 дал 7.7 м, значит проводка ω помогла» — оказалось
  выбросом −4.2σ от базы, которую тогда ещё не измерили.
- **Не поднимать kd против шумной производной.** Рост kd усиливает шум ровно настолько
  же, насколько демпфирует.
- **Не верить документации плагина/симулятора вместо замера.** Формула ветра ошиблась
  впятеро; предсказание «квадратично по скорости» тоже оказалось неверным (линейно).
- **Не менять источник сигнала «на всякий случай».** RAW_IMU (20.8 Гц) выглядел лучше
  ATTITUDE (12.5 Гц), а нёс тряску рамы 7.5 Гц — стало хуже.
- **Не править `src/lab/*.sh` во время прогона.** Bash дочитывает скрипт по офсету: сдвиг
  байтов увёл миссию на второй круг в тот же бэг и убил заливку видео.
- **Не менять две ручки сразу** и не сравнивать серии, снятые на разных мирах/разрешениях
  камеры: интринсики и текстуры входят в крутизну канала напрямую.
- **Не мерить паспорт датчика по бэгу, снятому до правки перцепта.** `L1_scale2ax` старше
  правки маски (`be8688f`), и паспорт по нему дал corr +0.09 при крутизне 0.414 — это
  задокументированный «до маски» S_lat=0.4 против 2.42 после. Слепой канал двухнедельной
  давности чуть не стал приговором рабочей оси. Сверять `# commit` в `.env` бэга.
- **Не настраивать ось, чья команда не пишется в бэг.** У `rate`-осей команды не было
  вовсе (`/flow_dbg5` шлёт только `pos`-оси) — сегменты пришлось резать по истинной
  скорости, и откат борта после торможения засчитался как ещё одна команда: три «проезда»
  на две команды миссии, разброс гейна 26%. Чинится записью цели (`rate_dbg` →
  `/flow_dbg7`), а не аккуратностью нарезки.
- **Не доверять юнит-тесту знака, если он писался под реализацию.** Тест крена БЫЛ и
  кодировал то же зеркало: снос ВЛЕВО гасился стиком ВПРАВО. Знак в тесте выводить из
  физики (контур — трекер скорости: ноль на выходе ⇔ измеренная скорость = заказанной),
  а не копировать из кода.
- **Не оставлять дефолты конфига расходящимися с тем, что летает.** У крена в конфиге
  годами стояли `kp=8, ki=2, imax=120, smooth=1`, а во всех прогонах через env жило
  `16 / 3 / 150 / 25`. Все замеры оси сделаны на лётных значениях; запуск без env давал
  НЕизмеренный контур. Победителя серии класть в конфиг сразу.
